# 개선 근거 보관

실제 버전을 확정하고 자료가 생길 때 `evidence/실제버전/before/`, `after/`, `validation/`을 만든다. 초기 구축에는 버전별 자료를 생성하지 않는다. [개선 일지 인덱스](../docs/iterations/README.md)와 [운영 절차](../docs/DEVELOPMENT-WORKFLOW.md)를 참고한다.

| 위치 | 자료 |
| --- | --- |
| before/ | 개선 전 UI·분석 응답·동작 결과 |
| after/ | 동일 조건의 개선 후 결과 |
| validation/ | 테스트 요약·Mock 정합성·수치 검산·시나리오 점검 |

자료마다 날짜, 생성 방법/명령, 기준 SHA 또는 미커밋 상태, 입력·case ID·데이터 기간, 기대/실제 결과, 환경(브라우저·화면 크기 포함), 제한을 적는다. 이미지 설명은 같은 폴더의 작은 Markdown 파일에 둬도 된다. 가능하면 동일 입력·시나리오·데이터·화면 조건을 유지하고 조건 차이가 있으면 명시한다. 파일명은 내용을 나타내고 기존 자료를 조용히 덮어쓰지 않는다.

테스트 통과는 실제 마케팅 효과나 인과관계의 입증이 아니다. 자동 캡처 불가·UI 미검증·실패도 일지에 명시한다. 자료가 없으면 링크를 만들지 않는다. `docs/cti-demo-preview.jpg`와 `docs/cti-decision-plan.jpg`는 기존 자료로 그대로 두고 촬영 조건 확인 후에만 참조한다.

비밀 키·계정·개인정보는 제거한다. 전체 node_modules·빌드 산출물·대용량 원시 로그·임시 파일을 넣지 않는다. 필요한 최소 로그와 검증 요약을 남기고, 큰 외부 자료는 보관 위치·접근 방법·무결성 정보를 기록한다.
