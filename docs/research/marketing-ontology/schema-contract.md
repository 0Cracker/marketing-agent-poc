# 공통 데이터 규격과 연결 계약

2026-10-14 최신 연결: [MC-1.0.0 스키마 대응표](common-contract/schema-crosswalk.md)와 [D003B 전수 필드 매핑](common-contract/d003b-mapping.json)을 추가했다. 기존 JSON Schema는 보존한다. RDF 표현과 SHACL 명세 검사 결과는 [실행 기록](common-contract/validation.md)에 있으며 원천 변환·적재는 승인/실행되지 않았다.

2026-10-14 개정: 첫 배치는 [D003B 원천 필드 표](first-batch-proposal.md)를 따른다. 제품/브랜드는T01, 캠페인/홍보 제품은T12에서 읽고 product_id/campaign_id로 연결한다. ‘지원 정의/공통 기준 정보102개’ 생성 제안은 철회했다. 아래40유형 JSON Schema는 선행 조사 초안이며 그 안의scope_id 등 참조 레코드를 첫 배치에 추가 생성하라는 뜻이 아니다. 첫 배치의 직접 필드를 기계 스키마로 옮기고 검사하는 작업은 값 생성 전에 수행한다.

2026-10-13. 상태: 설계 초안. [필드 사전](field-dictionary.md)에 40유형·공통10필드·유형별457필드 항목을 정의했고, [JSON Schema](schemas/marketing-records.schema.json)에 자료형·required·enum·일부 조건을 선언했다. 시간 계약 temporal을 공통 필수로 추가했고, 과거 집계용 HistoricalReport(H01)는 별도 정의로 분리했다. 필드 항목 수에는 서로 다른 유형에서 반복되는 의미가 포함된다. 457개의 수치 지표를 모두 채우라는 의미가 아니다.

최신 시간·집계·그래프 계약은 [temporal-design](temporal-design.md), 유형별 간격·기간·수량은 [temporal-catalog](temporal-catalog.md)를 따른다. Period.grain은 day/week/month/quarter/year/custom, 사건은 별도 시각 필드로 저장한다. temporal의time_kind·source_grain·series_role·달력·시간대·커버리지·available_at·revision은 필수다. metadata와 기존 원천 필드의 정합성은 실제 데이터 생성 후 의미 검사 대상이다.

새 가상값·예시 레코드·fixture는 아직 없다. 원천/사업 가정의 범위·값·문장은 [데이터 양 제안](data-volume-proposal.md)을 검토하고 승인한 뒤 별도의 완성 생성안에서 확정한다.

## 중요도와 스키마의 의미

| 구분 | 정의 | 생성·수집 방식 |
| --- | --- | --- |
| 필수 | 정체성·연결·질문 답변에 반드시 필요한 항목 | 확인된 값 또는 허용된 결측 상태를 가진 구조. 없는 사실을 발명해 필수를 채우지 않음 |
| 조건부 | 하위 유형·목표·원천 기능에 따라 필요한 항목 | 해당 조건이 참일 때 필요. JSON 조건으로 강제한 것과 의미 검증 대상으로 남긴 것을 구분 |
| 선택 | 추가 해석·필터링에 유용하지만 핵심 계약에 필수 아님 | 실제형 원천/승인 범위에 있는 항목만 채움 |

이것은 통합 분석용 규격이다. Google·Meta·Rakuten의 실제 응답 필드명과 1:1 동일하지 않다. API 원문→이 규격의 매핑을 별도로 보존해야 한다. T23 유통/배송, T25 주석/집계 등 서로 다른 단위는 record_kind와 조건부 필수값으로 구분한다.

## 자료형·단위

| 대상 | 규격 | 확인할 조건 |
| --- | --- | --- |
| ID | 비어 있지 않은 문자열, 전역 record_id와 원천 ID 분리 | source+scope+type 기준 중복·충돌 검사 |
| 시간 | date-time는 시간대 포함 ISO 시각, 기간은 date start/end_exclusive+IANA timezone | 시작<종료, 기간 경계·발생/게시/수집일 구분. 소스별 날짜 경계를 정규화 |
| 금액 | Money.amount는 소수 문자열, currency는 ISO 통화 코드 | 부동소수 오차 방지. 금액별 음수 허용 여부·소수점 자리·세금/환불 기준은 의미 검사 |
| 비율 | 내부 계산 ratio는 0–1 | 화면 %와 구분. 상대 증감은 부호가 있을 수 있고 별도 metric 정의 |
| 개수 | 전수 count는 0 이상 정수 | 추정 판매량·플랫폼 귀속 전환은 소수 가능. 같은 규칙을 모든 지표에 적용하지 않음 |
| 용량 | Quantity.amount+unit | ml/g 등 단위 매핑. 국가별 표시와 품목 변형을 확인 |
| 텍스트 | 원문·언어·record_ref+field_path·인용/offset | 발췌가 실제 원문에 존재. 감성/측면 라벨은 별도 파생값 |
| 결측 | null 가능 필드와 quality.availability/reason | 미확인·억제·미수집·해당없음 구별. 0·빈 문장으로 자료를 꾸미지 않음 |

기간 예시는 값으로 생성하지 않았다. 제안기간의 시작·종료·일수는 승인 문서에서 별도로 지정한다. 나라가 같아도 원천 계정/보고서 시간대가 다를 수 있어 scope 시간대로 몰래 바꾸지 않는다.

Money의 일반 구조는 조정값을 위해 부호를 허용하지만 가격·광고 지출의 실제 허용 범위는 데이터 종류별 의미 검사에서 제한한다. date/currency 패턴은 의미상 유효한 날짜·통화 목록 전체를 검증하지 않는다. format assertion을 켜고 국가별 계약을 추가해야 한다.

MetricValue.value는 숫자·Money·null을 허용한다. H01 등의 금액 지표는 Money(소수 문자열·통화)로, 개수·비율은 숫자로 저장한다. 어떤 지표에 어떤 자료형을 쓰는지는 MetricDefinition과 의미 검증에서 제한하며 금액을 무조건 부동소수 숫자로 바꾸지 않는다.

## 원천에서 그래프로 매핑

제품 행의product_id와 브랜드 필드, 캠페인 행의campaign_id와 대상 제품 필드를 사용한다. 브랜드를 노드로 표현할 때는 제품 행에서 같은brand_id를 묶어 만들며 별도 브랜드 원천을 추가 생성하지 않는다. 가격/리뷰/판매/재고는제품ID, 광고 성과는캠페인ID로 연결한다. 국가·판매처·창고는 해당 원천의 직접 필드로 보존한다.

지표 정의·분자/분모·집계 규칙은 제안서/스키마/코드에 정한다. 관리용 파일 이름·해시는 재현 기록이다. 이를 ‘공통 기준 정보’라는 가상 원천 목록으로 다시 만들거나 원천 건수에 더하지 않는다. 원천 건수와 적재 후 노드/관계 수는 별도로 보고한다.

## 반드시 지킬 데이터 간 정합성

1. SKU/변형→제품→브랜드, 국가별 offer, 리뷰 대상, 주문 대상의 참조가 실제 존재해야 한다.
2. 광고 설정의 유효기간과 성과 기간·광고 목적·귀속 정의가 맞아야 한다. 플랫폼 중복 귀속 매출은 합산하지 않는다.
3. 웹 거래 ID를 주문으로 대사한다. T17 일반 이벤트와 T18 커머스 이벤트의 같은 event_id는 중복 집계하지 않는다.
4. 주문 행 수량×단가−할인±세금의 정의된 합계와 주문 합계를 대사한다. 취소·환불을 중복 차감하지 않는다.
5. 재고는 자사 위치별 판매·확정/예정 입고와 일치시킨다. 경쟁 재고 수량은 내부 자료처럼 생성하지 않는다.
6. 리뷰 별점은 척도 이내, verified_purchase는 실제형 원천 범위와 일치한다. 한 리뷰가 여러 측면을 언급할 수 있다.
7. 같은 조사·정규화·시장/기간·수집범위에서 비율·비중을 계산한다. 별도의 소스 지수는 수요 건수로 바꾸지 않는다.
8. 발생·게시·수집·정정 시점을 구분한다. 변화 이후의 사건이 그 이전 변화의 원인으로 표시되지 않게 한다.
9. 실험 집단/기간/조건/표본과 결과를 구분하고 모의 반응 곡선은 관측 성과에 넣지 않는다.
10. 지원하지 않는 필드·미확인 사실은 unknown/결측/미수집으로 보존한다. 불필요한 필수값을 발견하면 값을 발명하지 말고 스키마를 수정한다.

JSON Schema로 자료형·필수 여부를 검사하고, 별도 참조/합계/시간/의미 검사로 위 규칙을 검사한다. 두 검사 모두 승인된 데이터가 생긴 뒤 실행한다. 스키마 컴파일 성공이 실제 자료의 정합성 성공은 아니다.

## 생성과 온톨로지의 반복 순서

1. 필드·연결 키·범위를 검토한다.
2. 완성된 생성 제안(규칙·크기·문장/사건·검사)을 보여주고 사용자 승인을 받는다.
3. 승인 범위의 일부 원천만 생성해 참조·대사·근거 발췌를 확인한다.
4. 질의 경로에 맞춰 최소 그래프를 적재하고 빠진 개체/관계를 찾는다.
5. 스키마·매핑 변경을 기록한다. 승인 밖의 새 값/사건/규칙이 필요하면 재제안한다.
6. 나머지 승인 자료를 확장하고 질문 커버리지·결측·반대 근거를 평가한다.

최종 온톨로지를 처음부터 완성하지는 않지만, 공통 키·범위·시간·출처 계약은 원천 생성 전에 맞춘다. 데이터와 온톨로지를 서로 연결 없이 독립 생성하지 않는다.
