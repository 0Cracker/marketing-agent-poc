# 캠페인과 매체 분류 조사

현재 PoC는 광고 운영 시스템, 분석용 채널, 실제 게재 서비스와 위치를 하나의 매체 선택기에 섞고 있어, 이름 축약보다 분류 축과 조회 역할을 먼저 분리해야 한다.

- 조사일: 2026-10-26, 공식 자료 열람 기준.
- 대상: 로컬 main `3c11e42`와 작업 중인 교육용 대시보드. 실제 광고 계정 연동 검증은 아니다.
- 상태: 공식 자료와 현재 구현 대조 완료, 조회 구조는 제안. 스키마 변경과 신규 데이터 생성은 수행하지 않았다.
- 구현 범위: 이번에는 표현과 맥락 유지, 정렬을 수정했다. 아래의 새 분류 선택기는 구현하지 않았다.

## 1. 핵심 구분

다음 표는 여러 공급자의 데이터를 통합할 때 필요한 개념 구분에 대한 설계 제안이다. 모든 공급자가 같은 필드와 계층을 제공한다는 뜻은 아니다.

| 개념 | 답하는 질문 | 예 | 주의점 |
| --- | --- | --- | --- |
| 사업 프로모션 | 회사가 어떤 활동을 추진하는가? | 여름 할인 | 여러 광고 시스템과 콘텐츠 협업을 묶을 수 있으나 명시적 연결이 필요하다 |
| 광고 운영 시스템 | 어디에서 광고를 만들고 집행하는가? | Google Ads, Meta Ads | Facebook과 Instagram 자체를 운영 시스템과 같은 단계에 놓지 않는다 |
| 광고 계정 | 어느 계정의 집행인가? | 공급자 계정 ID | 이름과 별도로 식별한다 |
| 플랫폼 캠페인 | 어떤 집행 관리 단위인가? | 플랫폼의 캠페인 ID와 이름 | 회사 프로모션이나 게재 위치와 동일하지 않다 |
| 캠페인 목표 | 어떤 사업 결과를 추구하는가? | 판매, 잠재고객 | 구매 이벤트나 입찰 최적화 목표와 분리한다 |
| 캠페인 유형 | 어떤 종류의 캠페인인가? | Google Search, Performance Max | 공급자별 값과 의미를 보존한다 |
| 광고그룹 또는 광고 세트 | 타깃과 광고를 어떻게 운영하는가? | Google ad group, Meta ad set | 통합 화면의 유사한 탐색 단계일 수 있지만 완전히 같은 객체는 아니다 |
| 광고와 소재 | 무엇을 보여 주는가? | 광고 ID, 이미지와 동영상 | 하나의 소재가 여러 광고에 쓰일 수 있으므로 동일시하지 않는다 |
| 게재 서비스 | 실제 어디에 노출됐는가? | Facebook, Instagram, YouTube | 하나의 캠페인에서 여러 서비스에 게재될 수 있다 |
| 게재 위치 | 서비스 안의 어느 공간인가? | 피드, 릴스, 검색 결과 | 캠페인의 고정 이름으로 대체하면 실제 분해가 어렵다 |
| 기기 | 어떤 기기에 노출 또는 방문했는가? | PC, 모바일 | 피드와 같은 위치 개념에 섞지 않는다 |
| 유입 출처와 방식 | 사이트 방문이 어디에서 어떻게 왔는가? | source, medium | 광고 관리 객체와 별도의 측정 차원이다 |
| 분석용 채널 | 어떤 규칙으로 방문을 묶는가? | Paid Search, Paid Social | 회사가 정한 콘텐츠 협업 분류와 GA4 기본 채널을 혼동하지 않는다 |

### 캠페인 이름의 역할

Google은 캠페인 이름, 마케팅 목표, 캠페인 유형을 서로 다른 설정으로 설명한다. 이름에 속성을 붙이는 관행 자체가 오류는 아니지만, 데이터 통합에서 이름을 해석해 속성과 관계를 복구하는 방식은 권하지 않는다. 원본 ID와 구조화된 속성을 기준으로 연결하고 이름은 표시와 검색에 사용한다. 이는 공식 설정 구분을 현재 PoC에 적용한 설계 판단이다. [Google 캠페인 설정](https://support.google.com/google-ads/answer/1704395?hl=en)

## 2. 공식 구조에서 확인한 사실

### Google Ads

기본 광고 관리 구조는 계정, 캠페인, 광고그룹, 광고로 이어진다. 각 객체는 ID와 resource name으로 식별한다. 캠페인 유형과 광고가 노출되는 네트워크도 별개다. Performance Max처럼 여러 네트워크에 걸치는 유형을 특정 게재 서비스 하나로 고정하는 모델은 충분하지 않다. [API 구조](https://developers.google.com/google-ads/api/docs/concepts/api-structure), [캠페인과 네트워크](https://developers.google.com/google-ads/api/docs/campaigns/overview)

따라서 `Google Ads → 검색광고 → 개별 캠페인`은 특정 범위에서 유용한 탐색 경로다. 그러나 모든 데이터의 고정 계층으로 강제하는 것은 별도의 설계 결정이며, 공식 구조 자체는 아니다. Performance Max 등 다른 유형에는 별도 탐색 단위가 필요할 수 있다.

### Meta Ads

Meta의 공식 SDK에는 캠페인, 광고 세트, 광고 객체가 있으며, 광고 세트는 `campaign_id`로 캠페인을 참조한다. Insights에는 캠페인 ID, 광고 세트 ID, 광고 ID와 별도로 `publisher_platform`, `platform_position` 분해가 존재한다. 공식 교육도 캠페인 목표와 광고 세트의 전환 위치, 이벤트, 성과 목표를 나눠 설명한다. [광고 세트 SDK](https://github.com/facebook/facebook-python-business-sdk/blob/main/facebook_business/adobjects/adset.py), [광고 SDK](https://github.com/facebook/facebook-python-business-sdk/blob/main/facebook_business/adobjects/ad.py), [Insights SDK](https://github.com/facebook/facebook-python-business-sdk/blob/main/facebook_business/adobjects/adsinsights.py), [Meta Blueprint](https://www.facebookblueprint.com/student/path/253165-selecting-objectives-course)

따라서 `Meta Ads → Facebook → 캠페인`을 유일한 원본 계층으로 만들면 캠페인이 여러 서비스에 게재되는 관계를 충분히 표현하지 못한다. 원본 관리 계층과 실제 게재 결과의 분해를 구분해야 한다. 게재 설정의 조작 위치는 상품과 자동화 설정에 따라 달라질 수 있어, 이 조사에서는 특정 위치에 항상 수동 설정할 수 있다고 단정하지 않는다.

Meta 개발자 문서의 Insights 분해 페이지는 조회 시 HTTP 429로 직접 열지 못했다. 분해 필드 존재는 Meta가 관리하는 공식 SDK로 확인했다. 실제 광고 계정에서 가능한 분해 조합과 지표 조합은 미검증이다.

### 네이버 검색광고와 블로그 협찬

네이버 공식 안내는 검색광고 등록 구조를 캠페인, 광고그룹, 키워드와 소재로 설명하며 광고 상품별 차이도 명시한다. 그러나 현재 PoC의 네이버 블로그 협찬은 네이버 검색광고 계정에서 집행한 광고라는 근거가 없다. 게시 서비스가 네이버라는 이유만으로 네이버 광고 시스템에 속한다고 변환하면 안 된다. [네이버 공식 광고 구조 안내](https://ads.naver.com/sub/insight/adtips/148)

### GA4

GA4는 source, medium, campaign, campaign ID, source platform, default channel group을 구분한다. 기본 채널 그룹은 규칙에 따른 방문 분류이며, 사용자 최초 획득, 세션, 이벤트 범위도 서로 다르다. PoC의 `channel=content`를 GA4의 특정 기본 채널로 자동 대응시키는 것은 근거가 부족하다. [유입 차원](https://support.google.com/analytics/answer/15612152?hl=en), [기본 채널 그룹과 범위](https://support.google.com/analytics/answer/9756891?hl=en)

UTM도 `utm_source`, `utm_medium`, `utm_campaign`, `utm_id`, `utm_source_platform`을 따로 제공한다. UTM 캠페인 값이 광고 플랫폼의 캠페인과 자동으로 같은 객체가 되는 것은 아니다. 수집 규약과 명시적 매핑이 필요하다. [공식 UTM 안내](https://support.google.com/analytics/answer/10917952?hl=en)

## 3. 현재 PoC와의 대조

확인 파일은 `shared/training-dashboard.d.mts`, `shared/training-dashboard.mjs`, `frontend/workbench/training-dashboard.tsx`, `scripts/training-data.mjs`와 기존 S16 화면 자료다. 전체 온톨로지에 없는 필드라고 단정하지 않고, 교육 대시보드에 전달되는 현재 계약을 평가했다.

| 현재 요소 | 확인된 상태 | 평가 |
| --- | --- | --- |
| `Campaign.platform` | Google Ads, Meta Ads, 가상 협찬 콘텐츠, 가상 협업 콘텐츠가 존재 | 운영 시스템과 협업 방식이 같은 필드에 섞임 |
| `Campaign.channel` | search, social, content | 광고 유형 계열과 집행 방식이 혼합됨. GA4 채널 규약이라고 볼 수 없음 |
| `Campaign.source` | google, facebook, instagram, naver_blog | 현재 조회에 쓰이지만 GA4 source와 동등한 수집 의미는 확인되지 않음 |
| `Campaign.adType` | search_ads, feed_ads, sponsored_content, influencer_content | 유형, 게재 형태, 협업 형태가 같은 수준에 놓임 |
| `Campaign.id`, `label` | 원본 참조와 표시 이름이 분리돼 있음 | 유지할 기반이 이미 존재함 |
| 캠페인 표시 함수 | 플랫폼과 유형, 목표 등을 붙인 이름으로 치환 | 원본 라벨보다 반복이 많고 분류를 이름에 의존하게 만듦 |
| 상단 매체 선택 | channel과 source 조합으로 선택지를 만듦 | 그룹과 그룹 전체, 세부 옵션이 함께 반복됨 |
| `Breakdown.placement` | 검색 결과, 모바일 피드, PC 피드, 콘텐츠 본문, all | 기기와 게재 위치가 일부 결합돼 있음 |
| 날짜별 성과 `Fact` | 캠페인과 기기로 집계 | 실제 광고 계정, 광고 세트와 광고 ID가 있는 실무 원본과 다름 |
| 분석 분할 | product와 traffic 등의 기존 분할 | 분할을 서로 합치면 중복될 수 있으므로 하나의 사실 집계로 무조건 결합하면 안 됨 |

목표에 관한 내용은 상세 운영 기록에 일부 있으나, 현재 Campaign 타입에는 독립적인 공급자 캠페인 목표 필드가 없다. 이름의 ‘구매전환’만으로 공식 캠페인 목표와 최적화 이벤트를 동시에 확정하면 안 된다.

현재 EDU-C3와 EDU-C4는 별도 캠페인 ID다. 둘 다 Meta Ads라는 이유로 하나의 실무 캠페인에 병합할 근거는 없다. 반대로 실무에서도 Facebook과 Instagram이 반드시 별도 캠페인이어야 한다고 학습시키면 안 된다.

## 4. 권장 조회 구조

분류 개념을 분리한다고 모든 개념을 상단 드롭다운으로 늘릴 필요는 없다. 다음은 사용자 실험 전의 UI 제안이다.

### 기본 조회

2026-10-26 후속 피드백에서 사용자는 세 선택기의 분류와 조작 부담이 여전히 크다고 지적했다. 따라서 기본 상단은 `캠페인 검색과 선택`, `필터 추가`로 줄이는 안을 권한다. 전체 캠페인에서 바로 이름이나 ID로 찾고, 필요한 경우에만 집행처와 기기를 좁힌다. 선택한 추가 조건은 해제 가능한 표시로 남긴다. 집행처에는 Google Ads, Meta Ads, 콘텐츠 협업처럼 현재 데이터의 집행 맥락을 구분할 수 있는 값을 제공한다. 집행처는 이 PoC의 UI 용어이며 광고 공급자의 공식 분류명은 아니다. 콘텐츠 협업을 가상의 광고 시스템으로 만들지 않는 것이 목적이다.

캠페인은 원본 이름과 ID로 찾을 수 있게 하고, 선택 목록의 보조 정보에 운영 시스템과 유형을 배치한다. 상위 집행처를 먼저 고르지 않아도 검색할 수 있어야 한다. 이름의 플랫폼, 위치, 목표 토큰을 반복해 나열하는 방식은 줄인다.

현재 데이터에는 ‘여름 할인’ 같은 별도 사업 프로모션명이 없다. 화면을 자연스럽게 보이게 하려고 임의 이름을 생성하거나, 현재 캠페인 이름을 그런 이름으로 일괄 변경하지 않는다.

### 추가 필터와 행 구분

게재 서비스, 위치, 목표, 광고 유형은 필요한 질문에서 추가 필터 또는 행 구분으로 제공한다. 조회 범위를 제한하는 필터와 같은 범위 안에서 행을 나누는 비교 기준은 구별한다.

예를 들어 `Meta Ads의 성과를 Facebook과 Instagram으로 비교`하는 질문에서는 집행처를 Meta Ads로 제한하고 행 구분을 게재 서비스로 선택한다. 현재 PoC에서 이 분해가 캠페인에 고정된 source에 의존한다는 한계도 함께 표시해야 한다. 실제 서비스별 게재 원본이 있는 것처럼 주장하면 안 된다.

소재나 게재 위치 필터를 상단 KPI까지 적용하려면 그 조건으로 매출과 비용을 일관되게 조회할 집계가 있어야 한다. 상세 표에만 있는 분할을 상단 KPI에도 적용한 것처럼 표시하지 않는다. 지원하지 않는 조합은 이유를 밝히고 선택을 제한하거나 해당 표의 조회 범위로 명시한다.

선택한 필터는 상단에 남기고, 호환되지 않는 캠페인을 해제했다면 이유를 알린다. 전체는 각 컨트롤에 한 번만 제공한다. 상위 그룹 제목과 같은 범위의 ‘전체’ 항목을 하나의 긴 목록에 반복하지 않는다.

## 5. 저장 구조와 집계에서 필요한 원칙

다음은 실무 연동을 위한 제안이며 이번에 추가한 필드가 아니다.

1. 원본 캠페인 이름과 ID를 보존한다. 통합 식별은 공급자 시스템, 계정, 원본 객체 ID를 포함해 설계한다. 이름이 같다는 이유로 연결하지 않는다.
2. 회사 프로모션과 플랫폼 캠페인의 연결은 별도 매핑으로 관리한다. 같은 기간과 상품이라는 이유만으로 같은 프로모션이라고 확정하지 않는다.
3. 관리 객체의 계층과 실제 게재 결과를 구분한다. 게재 플랫폼과 위치는 가능한 집계 수준의 관측 차원으로 보존하고, 캠페인의 단일 고정 속성으로 강제하지 않는다.
4. 캠페인 목표, 최적화 목표, 전환 이벤트, 입찰 전략을 구분한다. 원본 코드와 공통 분류를 함께 보존하고, 미확인은 미확인으로 남긴다.
5. 광고 노출, 콘텐츠 조회, 사이트 세션의 분모를 분리한다. 같은 source 이름이라는 이유로 CTR이나 조회율을 합치지 않는다.
6. 사실 집계의 단위를 명시한다. 캠페인 합계와 위치별 분해, 소재별 분해를 모두 더하면 비용과 매출이 중복된다.
7. 통화, 시간대, 귀속 기준, 보고 기준시점을 함께 확인한다. 플랫폼 귀속 매출과 GA4 매출을 같은 매출로 합산하지 않는다.
8. 공급자별 분해와 지표의 호환성을 확인한다. Google 공식 문서도 일부 분해가 행을 제한하거나 호환되지 않을 수 있음을 명시한다. [Google 보고서 분해](https://developers.google.com/google-ads/api/docs/reporting/segmentation)

조회 화면은 이 원칙을 사용자가 이해할 만큼만 표현하면 된다. 모든 원본 필드와 중간 계층을 기본 화면에 노출할 필요는 없다.

## 6. 적용 단계와 승인 경계

| 단계 | 할 일 | 데이터 영향 |
| --- | --- | --- |
| 1, 표현 개선 | 매출 정의, 기준시점, 자동 초기화 안내, 현재값과 증감 구분, 근거 가독성 | 기존 수치와 의미 보존, 이번 작업에서 수정 |
| 2, 선택기 정리 | 기존 필드에 기반한 집행처와 캠페인 선택, 보조 속성 분리 | 원본을 보존한 화면 표현안부터 확정, 이번에는 제안 |
| 3, 실무 계약 확장 | 계정과 원본 객체 식별, 공급자 목표, 공통 프로모션 연결, 실제 게재 결과 | 필드와 관계 변경이므로 개별 제안과 명시 승인 필요 |

3단계 제안 시에는 실제 사용 가능한 원본 필드, 신규 또는 변경할 타입과 관계, 결측 처리, 적용 레코드 수, 합계 검산과 되돌리기 방법을 먼저 명시해야 한다. 현재 여섯 캠페인의 병합, 목표 추정, 새 프로모션 이름 생성은 승인 범위에 포함되지 않는다.

## 7. 수용 기준과 사용자 검증

- 사용자가 Google Ads, Meta Ads와 Facebook, Instagram, 피드의 관계를 서로 다른 분류로 설명할 수 있는가?
- 같은 캠페인이 여러 게재 서비스에 나타나도 서로 다른 캠페인으로 오인하지 않는가?
- 집행처를 거치지 않고도 캠페인 이름 또는 ID로 원하는 대상을 찾는가?
- 사이트 방문의 source와 광고 운영 시스템을 혼동하지 않는가?
- ‘전체’ 선택과 개별 필터 해제의 결과를 예측할 수 있는가?
- 필터와 행 구분을 바꿔도 집계 범위와 비교 기준을 구별하는가?
- 현재값이 가장 낮은 집단과 하락이 가장 큰 집단을 각각 찾는가?
- 상세 기록을 보고 돌아온 후 사례, 기준시점, 기간과 필터를 설명할 수 있는가?

이는 실제 마케터 실험에서 확인할 과업이다. 성공률, 소요 시간, 학습 효과는 측정하지 않았다. 모바일 화면 설계와 검증은 사용자 요청으로 범위에서 제외한다.

## 8. 지표 상세와 상세 데이터의 역할 통합 제안

사용자는 주요 지표에서 상세 분석을 눌렀을 때와 상세 데이터 메뉴에서 다른 화면이 나오는 점, 설명이 많다는 점과 별도 메뉴의 존재 이유가 불명확하다는 점을 지적했다.

현재 전자는 지표별 차트와 계산에 연결된 수치, 집단 비교와 관련 기록을 보여 주며, 후자는 조사 목적별 표와 운영, 계측, 상품 자료를 보여 준다. 진입 기준이 지표와 조사 목적이라는 차이는 있으나 기능이 상당히 겹친다. 별도 메뉴로 유지해야 하는 필수 이유는 이번 검토에서 확인하지 못했다.

제안은 독립된 상세 데이터 메뉴를 지표 상세에 통합하는 것이다. 카드의 상세 분석은 모두 같은 구성의 화면으로 연결한다. 선택 지표의 추이, 연결 수치, 비교 표, 운영 근거 순서로 배치하되, 처음부터 설명과 모든 기록을 펼치지 않는다. 비교 표의 행 구분만 해당 지표에 적합한 캠페인, 기기, 소재, 상품 등으로 바꾼다. 결제 실패와 계측 불일치처럼 고유한 조사는 CVR, ROAS 상세의 관련 자료에서 접근 경로를 유지한다.

시나리오 설명은 테스트 케이스 영역으로 옮기는 안을 검토한다. 매출 범위와 현재 기간, 사례, 기준시점처럼 판단에 필수인 짧은 맥락은 화면에 유지하고, 산식의 긴 설명과 전체 기록은 필요할 때 연다. 이는 화면 구조 제안이며 이번 툴팁 수정에서는 메뉴, 선택기와 페이지 구조를 변경하지 않았다.

## 9. 후속 구현 결과, 2026-10-26

사용자가 캠페인 또는 집행처 중심 선택과 성과 현황 → 지표 상세 → 비교 표 → 운영 근거 경로를 요청하여 2단계의 화면 변경을 적용했다. 캠페인 검색과 Google Ads, Meta Ads, 콘텐츠 제휴별 선택, 상단 경로와 현황 복귀를 구현했다. 8절의 별도 상세 데이터 메뉴 통합 제안도 반영했다. [실제 구현 범위와 검증](../design/roas-training-dashboard.md#14-캠페인-선택과-단일-탐색-경로-2026-10-26)을 따른다. 앞선 제안 시점의 미구현 기록은 당시 상태로 보존한다.

현재 자료에 없는 광고 유형, 게재 위치나 목표를 추정해 추가하지 않았다. 콘텐츠 제휴 그룹은 현행 클릭당 정산 자료에 한정한다. 크리에이터 콘텐츠의 출처와 유료 집행은 함께 존재할 수 있으므로 일반적인 협업 여부를 광고 시스템의 배타적 하위 분류로 정의하지 않는다. [Meta 공식 파트너십 광고 교육](https://www.facebookblueprint.com/student/path/253173-partnership-ads-course)도 권한을 받아 크리에이터 콘텐츠를 광고에 활용하는 구조를 설명한다. 실제 공급자 계약과 데이터 모델 확장은 여전히 별도 승인 대상이다.
