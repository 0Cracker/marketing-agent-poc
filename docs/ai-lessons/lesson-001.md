## 1. 문제 상황

AI에게 데이터 명세와 원천 준비·검증을 연속해서 맡기면서 승인 범위, 공통 규격, 검증 수준, 구현 완료와 전체 완료의 경계가 여러 번 달라졌다. 같은 대화 안에서 그 차이를 짧은 표현으로 생략하면 사용자는 어떤 문제가 해결됐고 무엇이 남았는지 판단하기 어려웠다.

실제 구현에도 오류가 있었다. RDF 투영 중 만든 중간값을 재조회 결과처럼 비교한 검산 경로, 국가별 완전성과 정정판·DST 범위 선택 오류, 과거 HEAD에 고정된 보존 검사 등이 해당한다. 설명만 고치는 문제와 코드·모델을 검증해야 하는 문제를 나눠야 했다.

## 2. 사용자는 AI에게 어떻게 일을 맡겼는가

사용자는 목표·범위·자료 승인·업무 선택·운영 방식에 관여했고, AI는 이를 구체적인 파일·계산 규칙·코드·검사·보고서로 바꿨다. 모든 구현 선택을 사용자가 지시했다고 기록하지 않는다.

| 사용자가 결정하거나 요구한 것 | AI가 수행한 것 | AI가 대신 확정하면 안 되는 것 |
| --- | --- | --- |
| 기존 자료를 쓰고 새 자료는 계획부터 제시 | 부족 조건과 자료 수량·생성 규칙·검산 방법 제안 | 향후 모든 신규 값 생성의 포괄 승인 |
| 제시된 D006 보완 범위 승인 | 원천·스키마·독립 계산·메모리 오류 분기 구현 | 실제 공급자 자료를 확보했다는 주장 |
| 가상 반올림 선택 | 명시적 최소단위·Decimal 반올림 정책 구현 | 실제 판매처 결제 정책이라고 단정 |
| 현재 공통 구조 유지·D005 문서 정리 | 내부 규격과 목표 규격 구분, 변환·차이 검사 | 누락을 없애기 위한 공통 규격 완화 |
| OOPS를 외부로 보내지 않고 로컬 재사용 | 공식 엔진 설치·호출·소켓 차단·결과 판정 | 설치만으로 오프라인·모델 적합이 보장된다는 가정 |
| “보완안으로 다 해결가능한거야?” | 사전 보완과 OOPS 설계 검토의 효력 구분 | 아직 실행하지 않은 보완의 전체 성공 보장 |
| “사전은 뭔 사전”인지 설명 요구 | 용어·규칙·왜 차이가 났는지 설명 수정 | 사용자 이해가 확인됐다는 추정 |
| 작업 단위별 커밋 요청 | dev 규칙 확인, 파일 분류·검증·목적별 커밋 | push·main 반영·태그·Release까지의 권한 확대 |

원문 인용과 출처 등급은 [지시 대조표 U01~U10](../iterations/v0.2.0-double-diamond.md)에 정리했다. 저장소에 없는 과거 세부 프롬프트를 복원하지 않는다.

## 3. 시행착오와 교정 사례

### 사례 A. 진행 요청과 신규 자료 승인을 혼동

기존 일지에는 AI가 “ㄱㄱ”를 생성 승인으로 해석했다가 AGENTS의 개별 승인 조건을 확인하고 정정한 과정이 있다. 해당 시점의 생성은 0으로 기록됐다. 이후 사용자는 “기존 데이터 재사용 승인할게. 필요한데이터는 계획먼저 세우고 더 생성하도록해”라고 경계를 정했다.

AI는 재사용과 신규 생성의 scope를 분리하고, D006 승인 원문과 제안 범위 hash를 연결했다. 현재 330행 보완안도 별도 제안으로 남겨 당시 D006 승인을 소급 적용하지 않았다. 이미 승인된 재사용을 계속 묻는 것과 미승인 새 값을 임의 생성하는 것 모두 피해야 한다.

**상태:** 승인 경계 기록·실행 구분은 구현했다. 구체적으로 승인되지 않은 현재 보완값은 미생성이다. **재사용할 원칙 후보:** 일반 진행 문구를 모든 변경의 승인으로 확장하지 않고, 기존 승인은 해당 범위 안에서 재사용한다. [질문 재사용 승인](../research/marketing-ontology/common-contract/question-approval-20261015.json)·[D006 승인](../research/marketing-ontology/common-contract/d006-approval-20261016.json)·[이전 일지](../iterations/v0.2.0.md)가 근거다.

### 사례 B. “독립 검산”이라는 명칭만으로 검증을 신뢰

초기 RDF 검사는 투영 루프에서 만든 값과 원천을 비교했다. 이것은 저장된 그래프에서 실제 결과를 다시 읽었다는 증거가 아니었다. AI 이관 기록에서 이 한계를 확인하고, 원천의 별도 계산과 실제 RDF 재조회로 비교 경로를 바꿨다. 그 과정에서 TimeInterval의 scope·측정 역할 ID 충돌이 드러났다.

질문 검증에서도 국가 완전성, 정정판 혼입, DST 범위 선택 오류가 실제로 발생했다. AI가 조회와 oracle를 모두 작성했기 때문에 양쪽의 논리가 같은 방향으로 틀릴 가능성도 고려해야 한다. 테스트를 통과시키려고 원천이나 기대값을 바꾸는 대신, 실패한 사실과 범위 선택을 수정했다.

**상태:** 해당 실패를 재현·수정하고 회귀 통과를 확인했다. **한계:** 동일한 의미 명세의 오류나 독립적인 업무 전문가 판단까지 검증한 것은 아니다. **원칙 후보:** 함수·모듈을 나눈 사실과 독립된 검증 근거가 있는 사실을 구분한다. [D004 실패](../research/marketing-ontology/common-contract/runs/2026-10-15-d004-readback-1.json)·[CQ23 실패](../research/marketing-ontology/common-contract/runs/2026-10-15-cq52-authorized-1.json)·[D006 실패](../research/marketing-ontology/common-contract/runs/2026-10-16-d006-cq-ab-1.json)·[최종 회귀](../research/marketing-ontology/common-contract/runs/2026-10-16-canonical-system-2.json)를 따른다.

### 사례 C. 같은 이름의 “공통 규격”과 서로 다른 통과 기준

D005의 내부 공통 규격을 통과한 것과 프로젝트 전체 공통 사전의 필수 필드를 충족한 것은 달랐다. AI가 “공통”, “사전 미충족”으로만 보고하면 사용자는 원천 전체가 틀린 것인지, 규칙 연결이 덜 된 것인지 알기 어려웠다. 실제로 사용자가 사전의 정체와 미충족 이유를 다시 물었다.

설명을 필드 설명서·데이터 계약으로 풀고, 구조 변환·정보 부족·업무 의미·계약 검토를 구분했다. 기존 정보로 198행의 스키마 적합을 확보했지만, 나머지 330행의 보완안은 적용 전 제안으로 남겼다. “330행을 보완하는 안”과 “OOPS 106개까지 모두 해결하는 안”도 분리했다.

**상태:** 검사와 보고 구분은 구현·수정했다. 528행 전체 적합, OOPS 설계 해소, 사용자 이해 해소는 미확인이다. **원칙 후보:** 전문 용어를 처음 쓸 때 대상 규칙과 실패 단위를 정의하고, 제안의 목표와 확인된 결과를 따로 표시한다. [사전 검사](../research/marketing-ontology/common-contract/runs/2026-10-16-canonical-system-2-dictionary.json)·[미승인 보완안](../research/marketing-ontology/common-contract/canonical-followup-20261016.md)이 근거다.

### 사례 D. 질문 통과를 전체 완료로 확대

52시험에는 답을 내는 경우와 근거 부족·정책 위반으로 올바르게 보류하는 경우가 함께 있다. 모두 통과했다고 “52개 질문에 실질 답변 가능”이라고 표현하면 틀리다. 명세 검사·질문 검사·공통 사전·업무 의미·모델 검사도 각각 다른 검증이다.

AI는 52시험 중 실질 답변 28·보류/거부 24를 분리하고, 통합 실행기의 필수 게이트 결과로 fail·not_run·pass/complete를 계산하도록 했다. 질문·HermiT 회귀가 통과해도 사전과 OOPS가 남으면 전체는 fail/incomplete다.

**상태:** 현재 실행 보고서에서 이 구분을 확인했다. 실제 모든 게이트가 완료된 시스템을 운영한 사례는 아니다. **원칙 후보:** 결과를 “무엇이, 어떤 입력에서, 어디까지 통과했는가”로 보고한다. [질문 결과](../research/marketing-ontology/common-contract/runs/2026-10-16-canonical-system-2-questions.json)·[통합 판정](../research/marketing-ontology/common-contract/run-system-cycle.py)이 근거다.

### 사례 E. 사용자 선택과 외부 전송의 구체적 승인을 혼동

온톨로지 보강안의 “5A” 선택은 저장됐지만 특정 모델·목적지 전송에 대한 자동 승인 심사에서는 충분하지 않다고 판단됐다. 이는 사용자가 아무 의사도 표시하지 않았다는 뜻과 다르다. 승인 심사가 요구하는 구체성과 대화의 선택 수준이 맞지 않았던 사건이다.

그 뒤 사용자는 외부 전송을 반복하기보다 로컬 설치·재사용을 요구했다. AI는 외부 REST 실행을 제거하고 공식 엔진을 로컬 도구로 연결했다. 과거 실제 전송·보류 기록은 삭제하지 않았다.

**상태:** 현재 실행 경로는 로컬이며 모델 스캔의 외부 통신 시도는 0건이다. 이전 외부 전송 이력을 “한 번도 전송하지 않았다”로 바꾸지 않는다. **원칙 후보:** 승인 내용을 정확히 기록하되 이미 달라진 요구를 과거 승인 보류로 계속 막지 않는다. [과거 실제 전송 승인](../research/marketing-ontology/common-contract/oops-approval-20261015.json)·[보류 기록](../research/marketing-ontology/common-contract/oops-approval-20261016.json)·[로컬 실행 안내](../research/marketing-ontology/common-contract/local-validation.md)를 따른다.

### 사례 F. 로컬 도구라는 이유로 통신·정확성을 가정

공식 OOPS를 설치해도 P41은 외부 Licensius에 모델을 보낼 수 있었다. CLI 종료코드 0도 모델 적합을 뜻하지 않았다. 업스트림 시험 실패에는 도구의 순회 예외, 직렬화 비교기·기대 설명문 문제와 외부 규칙 적용 범위가 섞여 있었다.

AI는 호출 코드를 읽고 소켓 차단을 실제로 확인했으며, 공개 URL/외부 서비스 규칙의 비적용 사유를 기록했다. 최소 패치와 원본·중간 실패를 보존하고 오프라인 프로필을 검증했다. 도구 시험 33개 통과와 모델 지적 106개 미해결을 구분했다.

**상태:** 현재 고정 엔진·Java 17 환경에서 로컬 실행을 확인했다. 다른 버전의 동일 동작이나 모든 모델 설계의 정확성을 보장하지 않는다. **원칙 후보:** 설치·프로세스 성공·검사 실행·발견 사항·최종 적합을 따로 판정한다. [패치 기록](../research/marketing-ontology/common-contract/oops-local-fixes.json)·[모델 실행](../research/marketing-ontology/common-contract/runs/2026-10-16-canonical-system-2-logic.json)·[도구 시험 근거](../research/marketing-ontology/common-contract/runs/2026-10-16-canonical-final-integrity-2.json)를 따른다.

### 사례 G. 누적 작업과 “원본 보존”이 정상 커밋을 막음

사용자는 작업 분리가 부족해 Git 관리가 어렵다고 지적했다. AI는 목적별 커밋을 만들면서 D005의 Git 보존 검사가 최초 생성 HEAD·index에 고정돼 정상적인 후속 커밋도 거부하는 문제를 발견했다. 디스크 원본이 같더라도 Git 객체의 줄바꿈 바이트가 다른 문제도 있었다.

원래 생성 기록은 유지하고 읽기 전용 validate/cycle의 기준을 실행 시작 상태로 바꿨다. 연구 자료의 바이트 보존과 CRLF 공백 검사 규칙을 보정하고, 줄바꿈만 다른 10파일을 별도 커밋했다. 보호 60파일을 Git 객체와 직접 대조했으며 새 HEAD의 D005 검사도 통과했다. 다른 워크트리의 feature 브랜치 진행은 자신의 변경과 구분했다.

**상태:** 11개 로컬 커밋과 당시 clean 상태를 확인했다. 모든 중간 커밋을 독립 실행한 것은 아니다. **원칙 후보:** 보존의 시간 범위와 대상을 먼저 정의하고, 목적·의존 관계·검증을 작업 중 기록한다. [커밋 후 회귀](../research/marketing-ontology/common-contract/runs/2026-10-16-post-commit-d005-1.json)·[바이트 무결성](../research/marketing-ontology/common-contract/runs/2026-10-16-commit-split-integrity-1.json)이 근거다.

| --- | --- |
| 확인된 결과 | 실제 실패 ID·원인·수정 후 회귀가 존재한다. 승인 scope·입력 hash·상태 분리·Git 바이트 검증을 구현했다. |
| 해결하지 못한 문제 | 공통 사전 330행과 OOPS 106개, 전체 필드 업무 의미 검토는 남았다. |
| 설명의 개선 | 사용자 질문을 계기로 사전·행수·지적 수·완료 수준을 구분해 설명했다. 이해 해소 여부를 측정하지 않았다. |
| 측정하지 않은 효과 | AI 사용으로 절약한 시간, 프롬프트 개선의 인과 효과, 다른 모델 대비 성능, 사람만 작업했을 때의 결과 |
| 후속 적용 후보 | 범위·산출물·검증·남은 쟁점을 함께 지시하고, 이미 승인된 범위와 새 판단을 구분한다. 적용 후에도 실제 실패·보류 기록을 확인한다. |

사용자가 작업의 의미와 범위를 결정하고 AI가 구현·검산·기록을 수행하는 역할 분담은 관찰됐다. 이 한 사례를 근거로 사용자의 업무 방식 전체나 AI의 보편적 성공 방법을 확정하지 않는다.
