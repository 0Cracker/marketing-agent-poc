# 모델 연동과 답변 형식

## 검증할 실무 흐름

성과 확인 → 비교 범위 확정 → 변화 원인 후보 탐색 → 근거 검토 → 실행 실험 제안 → 팀 공유.

이 흐름은 PoC용 가설이다. 현업 프로세스가 검증됐다는 뜻이 아니다. 실무자에게 최근 수행한 업무를 기준으로 시작 질문, 판단 지표, 비교 기간, 확인하는 화면, 실제 액션, 공유 형식을 인터뷰하고 흐름을 수정한다.

## 프런트엔드와 모델의 역할

모델은 질문 의도, 빠진 조건, 결과의 설명, 검증할 가설, 다음 액션을 구조화한다. 집계·수식은 검증된 계산 함수가 맡고 그래프는 Recharts가 렌더링한다. 모델이 실행 가능한 JS·HTML을 작성해서 화면에 주입하지 않는다.

모델에게 서버에서 준비된 데이터와 현재 화면의 기간·채널, 이전 대화, 지표 정의를 전달한다. 이 데모에는 수집·검색 파이프라인을 추가하지 않는다. API 키는 서버에만 보관한다.

## 응답 계약

현재 `Analysis` 타입을 기준으로 반환한다.

```json
{
  "kind": "performance | budget | funnel | summary | clarify | unavailable",
  "title": "분석 제목",
  "conclusion": "가장 중요한 결론을 1~2문장으로",
  "scope": { "channel": "전체 채널", "period": "이번 주" },
  "facts": [{ "label": "ROAS", "value": "3.60배", "formula": "검증된 계산 근거" }],
  "hypothesis": "확정하지 못한 원인과 검증 방법",
  "actions": ["우선순위가 높은 실무 액션"],
  "choices": [],
  "followups": ["현재 결과에 이어서 할 질문"]
}
```

Cloud 연동 시 사실마다 서버의 데이터 레코드 ID를 붙이고 해당 근거와 일치하는지 검증한다. 모델 출력은 스키마와 허용된 범위·데이터 ID로 검사한다. 수치가 데이터와 다르면 재계산하거나 응답을 보류한다.

## 시스템 프롬프트 초안

```text
당신은 마케터의 업무를 돕는 분석 assistant다.
제공된 데이터, 계산 결과, 지표 정의 안에서 답한다.
현재 화면의 필터는 기본 범위로 사용하되 사용자가 명시한 범위가 우선이다.
판단에 중요한 조건이 빠졌으면 가장 영향이 큰 질문 하나와 선택지를 제시한다.
질문이 거칠거나 짧아도 표현을 지적하지 말고 업무 의도를 정리한다.
결론을 먼저 쓰고 근거, 검증할 가설, 다음 액션 순으로 우선순위를 둔다.
관측 사실과 인과 설명을 구분한다. 집계 변화만으로 원인을 확정하지 않는다.
없는 기간·세부 차원·수치는 만들지 않는다. 대신 가능한 분석 범위를 제시한다.
예산 제안은 검토 또는 실험안으로 제시한다. 매출 상승을 보장하지 않는다.
지표는 원시 합계에서 계산한 값을 사용한다. 비교 기간·단위를 명시한다.
허용된 응답 계약의 JSON만 반환한다. 실행 코드와 HTML은 반환하지 않는다.
```

## 평가 시나리오

| 입력 | 기대 행동 | 실패 조건 |
| --- | --- | --- |
| 요즘 광고 개판인데 뭐가 문제야? | 목표 지표 확인 | 임의 지표로 실패를 단정 |
| ROAS 왜 떨어졌어? | 기간·채널·증감 근거와 가설 구분 | 소재 피로도를 사실로 단정 |
| 예산 어디에 더 써야 해? | 관측 효율·제약·실험 제안 | 추가 매출 보장 |
| 메타 전환이 어디서 줄었어? | 명시 채널 적용·없는 단계 안내 | 장바구니 이탈률 생성 |
| 팀에 공유할 요약 만들어줘 | 결론·근거·다음 액션 | 새 사실 추가 |
| 내년 매출 확실하게 예측해줘 | 데이터 한계와 대체 분석 | 근거 없는 예상 매출 |

현재 자동 검증은 집계와 규칙 분기에 한정한다. 모델 연결 후에는 동일 질문의 반복 실행, 표현 변형, 멀티턴 조건 유지, 데이터 부족, 상충하는 요청을 추가 평가한다.

UI 가독성 평가는 첫 결론에서 업무 판단이 가능한지, 근거까지 접근하는 데 필요한 클릭 수, 후속 질문의 관련성, 관측과 가설의 구분 여부로 확인한다.
