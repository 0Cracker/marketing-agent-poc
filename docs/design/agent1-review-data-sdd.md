# Agent1 리뷰 데이터 SDD, 최신 Intent 반영 개정안

상태: **intent-to-done 2단계, SDD 세부 인터뷰 진행 중, 인터뷰 1(분류 체계 B안), 인터뷰 2(원문/분류 별도 저장 B안), 인터뷰 3(1차 전수 분류 + 2차 전수 검수 B안), 인터뷰 4(검수 이견 협의 후 미합의 건 제3자 판정 A안), 인터뷰 5(공통 상품 메타데이터 별도 파일 A안), 인터뷰 6(coverage 4건 각각 양 기간 명시 A안) 확정, 전체 SDD 승인 전** (2026-11-03, Asia/Seoul). **신규 리뷰 파일 생성 0건, 코드 변경 및 인수 테스트 구현 미실행.**
우선순위: [최신 Agent1 Intent](agent1-intent.md) > [리뷰 48건 제안과 승인 기록](../research/marketing-ontology/data-proposal.md) > 이 문서의 기존 초안 및 과거 제안. 최신 Intent와 충돌하는 과거 문장은 이 설계에 적용하지 않는다.
목적: **48건 리뷰 원문의 품질, 의미 다양성, 유사 리뷰 최소화, 정합성, 분석 적합성**을 우선 명세하고, UI에 필요한 데이터 정합성 계약은 범위 경계로만 유지한다. **화면에서 원문을 어떻게 제공, 배치, 조회할지는 [별도 UI/UX SDD](agent1-review-ui-sdd.md)의 책임**이다. 2026-11-03 사용자 지시에 따라 **앞서 제시한 SDD 인터뷰 7(두 기간 원문의 화면 제공 방식)은 선택되지 않았고 데이터 SDD에서는 해당 선택 인터뷰를 진행하지 않는다.** 기간별 원문 ID의 참조 정합성은 데이터 검증 의무로 남기되 UI 구현 방식을 여기서 확정하지 않는다.
시각화: [데이터 SDD 검토용 HTML](agent1-review-data-sdd-visual.html). 확정 배분과 규칙, 미승인 설계의 차이를 보여 주는 **설명용 인터랙티브 문서**이며 실제 리뷰 원문, 조회 API 또는 대시보드 구현이 아니다.

## 2. 원문 배분, 판매처와 제공 범위

판매처는 **자사몰**과 **가상 외부 판매처 1개**의 두 종류다. `sourceId`의 구체 코드와 사람이 읽는 `sourceName`은 고정 매핑으로 검증하며, 실제 상호명이나 판매처 실측 자료로 표현하지 않는다. 아직 코드 값은 확정하지 않았다.

| 사례 | 작성기간 | 자사몰 | 가상 외부 판매처 | 소계 |
| --- | --- | ---: | ---: | ---: |
| S16 | 비교기간, baseline | 4 | 8 | 12 |
| S16 | 분석기간, current | 8 | 4 | 12 |
| S17 | 비교기간, baseline | 8 | 4 | 12 |
| S17 | 분석기간, current | 4 | 8 | 12 |
| **합계** | 비교기간 24, 분석기간 24 | **24** | **24** | **48** |

- S16, S17 각각 **24건**, 각 사례의 두 기간 **12건씩**, 총 **48개의 서로 다른 리뷰 ID**를 갖는다. 같은 ID가 복수 카테고리에 매핑되어도 원문 레코드 수는 늘지 않는다.
- 제공 범위 선언(`coverage`)은 **S16/S17 × 두 판매처 = 4개**이며, **인터뷰 6 A안 확정:** 4개 선언 각각이 사례, EDU-P1, 판매처를 식별하고 **`periodIds: ["baseline", "current"]`로 두 작성기간을 명시**한다. 실제 기간 시작/끝은 기존 ROAS 사례의 기간 정보를 참조하고 리뷰 파일에 날짜를 중복 저장하지 않는다. 제공 선언은 리뷰 수에 합산하지 않고, 기간 ID가 하나라도 없거나 중복/알 수 없는 값이면 유효한 제공 선언으로 간주하지 않는다. 해당 필드를 포함하는 신규 원시 파일 스키마 자체는 별도 승인 대기다.
- 전 사례의 EDU-P1 품목은 샴푸여도 **원문 제공 선언은 S16/S17에만** 있다. 다른 사례와 EDU-P2/P3에 빈 리뷰 배열을 생성해 '제공된 0건'으로 오인시키지 않는다.
- 부정/긍정 언급과 별점의 배치는 원문 증거에 맞아야 하며, `rating`만으로 분류를 결정하지 않는다. 단순 조사, 상품명, 말투만 바꾼 복제뿐 아니라 **표현은 다르지만 핵심 경험과 근거가 사실상 같은 리뷰의 반복**도 품질 결함 후보로 검수한다. 단, 같은 제품 특성에 대한 실제로 구별되는 경험이나 정반대 평가는 중복으로 자동 제거하지 않는다.

## 3. 작성일, 수집일, 기간 및 보고 기준

**시간대:** `Asia/Seoul`의 `+09:00` 오프셋을 명시한 ISO 8601 일시를 사용한다. 저장 문자열 비교가 아니라 유효 일시 파싱과 현지 날짜 경계로 검증한다.

| 기간 ID | 작성시각 범위, 시작 포함 및 끝 미포함 | UI 해석 |
| --- | --- | --- |
| `baseline` | `[2026-08-03T00:00:00+09:00, 2026-08-17T00:00:00+09:00)` | 비교기간, 08-03~08-16 |
| `current` | `[2026-08-17T00:00:00+09:00, 2026-08-31T00:00:00+09:00)` | 분석기간, 08-17~08-30 |

- **기간 귀속:** 오직 `writtenAt`이 속한 기간으로 판정한다. 수집일이 어느 기간인지는 기간 배분에 사용하지 않는다.
- **자료 확보:** `writtenAt <= collectedAt < asOf`를 만족하는 리뷰만 해당 보고 기준의 조회에 포함한다. 초기 `asOf`는 2026-08-31 00:00+09:00, 후속은 2026-09-07 00:00+09:00. 승인된 48건은 모두 **초기 보고 기준 이전 수집**이므로 두 스냅샷의 이 48건 수와 내용은 동일해야 한다. 이 시점 뒤의 추가 리뷰를 묵시적으로 생성하지 않는다.
- **예시 판정:** 08-15에 작성하고 08-18에 수집한 리뷰는 08-31 보고 기준에 확인 가능하면 **비교기간 리뷰**다. 반대로 08-30 작성, 08-31 00:00 이후 수집 자료를 08-31 보고서에 넣으면 안 된다. 뒤 경우는 경계 검증용 입력의 개념 예시일 뿐 신규 저장 레코드가 아니다.
- 작성일은 제품 사용일, 구매일, 배송일, 원인 발생일과 **동일하다고 가정하지 않는다**. ROAS 변화보다 늦게 작성된 리뷰를 과거 ROAS 변화의 확정 원인으로 역연결하지 않는다.
- 사용자 지정 조회 기간은 이 SDD의 **두 기간 안에서만** 적용한다. 지원하지 않는 기간을 임의 확장하지 않는다. 보고 기준이 없는 요청, 잘못된 시간 문자열 또는 알 수 없는 스냅샷은 검증 오류다.

## 4. 사례별 분석 적합성 A, B, C

세 항목은 **각 사례에서 모두** 충족한다. 별점/문구를 생성하면서 '정답 원인'을 심지 않고, 독립 검수자가 원문 ID와 계산을 근거로 확인한다.

| 사례 | A, 같은 평가 측면의 상반된 경험 | B, 전체와 판매처별 추세 차이 | C, 시간 순서의 함정 |
| --- | --- | --- | --- |
| S16 | 같은 EDU-P1, 동일 작성기간, 같은 상위 측면에 서로 반대되는 구체 경험을 설명한 **서로 다른 두 원문 이상**. 판매처 일치 여부도 검수표에 기록 | 자사몰 4→8, 외부 8→4로 표본 구성이 바뀐다. 전체 평균 별점 **또는** 특정 상위 카테고리 언급 비율의 변화 방향과 최소 한 판매처 내부 변화 방향이 달라야 한다 | 비교기간 작성, 분석기간 수집 사례를 포함하고, 08-17 이후 작성된 리뷰를 08-17 전후 ROAS 변화의 선행 원인처럼 오인할 여지가 있는지 점검 |
| S17 | S16과 **별도의** 같은 측면 상반 경험 원문 쌍. 상충한 평가를 오류라고 단정하지 않게 원문이 각각 구체적이어야 함 | 자사몰 8→4, 외부 4→8의 역방향 구성이다. 전체와 판매처 내부 추세의 방향 차이를 **S17 자체 원문**으로 독립 검증 | 비교기간 작성, 분석기간 수집 사례와 후기 작성 시점이 ROAS 관측 이후인 사례를 포함하고 선후 주장의 한계를 검사 |

**A 판정:** 두 리뷰의 `caseId, productId, periodId, categoryId`가 일치하고 원문 증거가 각각 상반된 세부 경험을 지지해야 한다. 같은 리뷰에 상반 경험이 함께 적혔다면 양쪽 분류는 허용하지만 이것 **한 건만**으로 '두 고객 경험' 요건을 충족시키지 않는다.

**B 판정:** 기준 지표를 검산표에 먼저 고정한다(평균 별점, 또는 해당 그룹의 전체 리뷰 수를 분모로 하는 상위 카테고리 언급 비율). 두 기간의 분모가 모두 존재하고 실제 방향이 0이 아닐 때 **`(전체 현재-비교) × (해당 판매처 현재-비교) < 0`**인 출처가 하나 이상 있어야 한다. 즉 양쪽 변화가 모두 0이 아니고 부호가 정반대여야 한다. 한쪽이 변화 없음(0)인 경우는 차이 후보로 설명할 수 있어도 이 SDD의 B 합격으로 세지 않는다. 단순 건수 변화나 판매처 구성비 이동만으로 '평가 추세 반전'이라고 판정하지 않는다. 전체 평균은 판매처별 **별점 합계 / 총건수**, 전체 카테고리 비율은 **중복 제거한 언급 리뷰 수 / 총건수**로 재계산한다. 이 규칙으로 구성 변화와 각 판매처 자체의 변화를 구분한다. 양쪽 판매처가 모두 역전되는 강한 Simpson 사례는 가능하지만 필수 조건으로 추가하지 않는다.

**C 판정:** 작성시각과 수집시각의 경계 통과 사례를 각 1건 이상 확보해 기간과 가용 시점을 구별하며, ROAS 변화와 후기 작성 선후를 나란히 대조할 수 있어야 한다. 각 사례의 `writtenAt` 이후 원문만으로 사건 이전의 인과를 확정하는 설명은 **불합격**이다. 개별 구매일과 경험 발생일이 없다는 한계를 검수 결론에 명시한다. 08-31 이후 수집 경계는 승인된 48건의 배분을 바꾸지 않고 **격리된 계약 검증 입력**으로 시험하는 계획이며 이번에 생성하거나 테스트를 구현하지 않는다.

### 4.1 리뷰 원문 다양성 및 유사도 품질, 사용자 추가 중점(2026-11-03)

**이번 데이터 SDD의 우선 목표는 48건의 고유 ID 확보가 아니라, 원문별로 구별 가능한 고객 경험과 맥락을 확보하는 것**이다. 같은 문장을 재배열하거나 표현만 교체한 48건은 품질 통과로 보지 않는다. 이는 리뷰 내용 품질에 대한 요구이며, 신규 리뷰나 테스트 데이터의 즉시 생성 승인 또는 숫자 배분 변경은 아니다.

- **중복 금지:** 공백, 문장부호, 불필요한 상투 표현만 다른 사실상 동일한 원문은 금지한다. 동의어로 치환해도 대상 특성, 평가 방향, 근거, 사용 맥락이 사실상 같은 리뷰라면 **의미상 중복 후보**로 잡아 수작업으로 판정한다. 다른 사례, 기간, 판매처에 분산되어 있다는 이유만으로 중복을 허용하지 않는다.
- **경험의 구별성:** 같은 향 또는 사용감 측면을 언급하더라도 평가 이유, 강도, 상황, 기대와 실제 경험, 복합 장단점 중 **실제로 원문에 드러난 차이**가 있어야 별도 사례로 의미가 있다. 차이를 만들려고 근거 없는 구매, 광고 유입, 피부 상태나 실험 효능을 꾸며 넣지 않는다. 한 원문에 여러 측면이 함께 등장하는 자연스러운 혼합 평가도 허용한다.
- **자연스러운 편차:** 시작과 끝 문구, 문장 길이, 말투, 별점과 평가 방향의 조합이 일정한 틀을 기계적으로 반복하지 않도록 검토한다. 모든 원문에 동일한 상세정보를 강제로 넣거나 5개 상위 카테고리를 기계적으로 균등 배분하지 않는다. 소규모 합성 자료를 실제 표본의 대표성으로 주장하지 않는다.
- **다양성 점검표:** 원문별 `reviewId`, 핵심 경험 요약, 근거 문구, 분류 측면, 평가 방향/복합성, 구별되는 구체 맥락을 **검수용 내부 기록**으로 대조한다. S16/S17, 비교/분석기간, 자사몰/외부의 8개 셀을 교차 확인하되 **기존 4/8, 8/4 배분과 총 48건을 유지**한다. 분석 적합성 A/B/C를 맞추려고 같은 경험을 여러 사람의 리뷰처럼 복제하거나 비현실적인 별점/표현 패턴을 만들지 않는다.
- **검출과 최종 판정:** 전체 48건의 고유한 두 리뷰 쌍 **1,128쌍**을 대상으로 정규화 문자열 일치 및 어휘/의미 유사도 **후보 탐색**을 계획한다. 수치 유사도는 검토 후보를 찾는 보조 수단이며 **임의의 임계값만으로 의미 중복 또는 비중복을 확정하지 않는다**. 표시된 후보를 1차 분류 담당자와 별도 2차 검수자가 원문/구체 경험으로 판단하며, 논쟁이 남으면 인터뷰 4에서 확정한 협의 후 제3자 판정 절차를 따른다.
- **합격 경계:** 정규화한 원문 완전 중복 **0쌍**, 차별화할 근거가 없는 의미상 중복의 **미해결 건 0건**, 48건 전수 검수 이력, 사례별 A/B/C 근거 보존을 요구한다. 의미상 유사하지만 고객 경험 차이가 충분한 두 원문은 **구별 근거를 기록하고 유지 가능**하다. 실제 유사도 결과/비율 또는 품질 통과는 **원문 48건이 아직 없으므로 주장하지 않는다**.

## 5. 원시 데이터 계약, 보존 및 신규 변경 제안

### 5.1 기존에 승인 기록이 있는 리뷰 원시 묶음, 미구현

[기존 승인 기록](../research/marketing-ontology/data-proposal.md#2026-11-02-현재-roas에-리뷰만-추가-최소-생성-제안)은 **48개 리뷰, 제공 선언 4개, 별도 파일 `data/roas-reviews.json` 및 `roas-reviews/1` 제안**을 다룬다. 기존 초안과 기록의 승인 표기에는 앞부분 '명시 승인'과 뒤쪽 '미승인'이 혼재하므로, **확인된 48건 생성 승인과 이번 SDD/추가 필드의 승인 여부를 별도로 취급**한다. 데이터, 코드 구현 승인은 이 문서에서 추정하지 않는다.

| 구조 | 설계상 최소 필드와 조건 |
| --- | --- |
| 최상위 | `contract="roas-reviews/1"`, `subjectCategory="shampoo"`, `coverage[]`, `reviews[]`. 합성/비대표 표본임을 묶음 맥락에서 알린다. |
| 리뷰 | `id`(전역 고유), `caseId`(S16/S17), `productId`(EDU-P1), `sourceId`, `sourceName`, `writtenAt`, `collectedAt`, `rating`(1~5 정수), `ratingScale=5`, `text`(공백 아닌 한국어 원문). |
| 제공 선언 | **인터뷰 6 A안 확정:** 사례, EDU-P1, 판매처를 식별하는 **4개 선언 각각**에 `periodIds: ["baseline", "current"]`를 명시한다. 기간 ID의 실제 날짜 범위는 해당 사례와 스냅샷의 기존 ROAS `periods`에서 참조한다. **4개 선언의 내용과 기간 표현 설계는 확정**, 이를 담는 파일 스키마와 배포 계약은 별도 승인 대상이다. |
| 금지 | 리뷰에 `campaignId`, `device`, `orderId`, `customerId`, `sessionId`, 개인 광고 접점, `cause`/정답/가상의 구매 인증을 임의로 부여하지 않는다. |

제공 선언이 없는 사례를 '미제공'으로 해석하는 것은 **검증을 통과한 전체 S01~S18 범위 카탈로그에 대해서만** 허용한다. 원시 파일 누락, 해시 오류, 선언 유실 및 잘못된 참조는 '미제공'이 아니라 **오류**다. 초기 승인 4개 선언은 실제 파일 생성 전까지 존재하지 않는다.

### 5.2 사용자 확정 설계 방향과 추가 스키마 승인 대기

1. **전 사례 샴푸 정의, SDD 인터뷰 5 A안 확정(2026-11-03):** 기존 `products[]`에는 `category`가 없으므로 **별도 공통 상품 메타데이터 파일**에 `EDU-P1 → 샴푸` 매핑을 **한 번만 정의**하고 S01~S18 전 사례에서 동일하게 참조한다. 원시 `training-dashboard.json`에 상품별 `category` 필드를 추가하지 않고 각 사례에 품목값을 중복 저장하지 않는다. 기존 EDU-P1 식별자, 표시명 '교육용 자사 상품 1', 정가 25,000원, EDU-P2/P3의 상품 정체성, 기존 KPI/기간/가격과 원천 바이트를 보존한다. S16/S17 리뷰의 `subjectCategory`만으로 전 사례 공통 정의를 대체하지 않는다. **별도 파일이라는 설계 방향은 사용자 확정**, 파일 경로, 계약명, 정확한 필드/타입, 무결성 해시와 배포/로더 등록 방법은 **신규 메타데이터 스키마 승인 전 미확정**이다. 특히 기존 `manifest.metadata`에 단순 추가하면 필수 로더 오류가 ROAS에 전파될 수 있어 §5.2 4항의 **오류 격리 선행 조건**을 적용한다.
2. **분류 결과 별도 저장, SDD 인터뷰 2 B안 확정(2026-11-03):** 리뷰 원문과 분류 결과는 **서로 다른 파일**로 관리한다. 원문 파일의 `reviews[]`에 `categories`를 추가하지 않고, 별도 분류 파일이 **원문 `reviewId`로 참조**한다. 분류 오류 수정이나 세부 경험 확장 시 분류 파일만 갱신하며 원문 48건, 작성일, 수집일, 평점, 판매처와 기존 ROAS 값은 바꾸지 않는다. 무결성 확보를 위해 원문 해시, 분류 사전 버전, 분류 파일 버전을 대조하고 변경 후 집계를 재검산한다. **별도 파일이라는 방향만 확정**되었고 후보 경로 `data/roas-review-classifications.json`, 계약명 `roas-review-classifications/1`, 개별 필드/타입, 데이터 생성, 배포 방식은 **추가 스키마 승인 대상**이다.
3. **coverage 완결성, 인터뷰 6 A안 확정:** 4개 제공 선언 **각각**에서 `periodIds: ["baseline", "current"]`를 직접 명시한다. 기간의 실제 시작/종료 시각은 기존 ROAS 사례의 `periods`를 참조하며 별도 날짜를 중복 기입하지 않는다. 제공 선언 ID 조합 중복, 기간 누락/중복, 알 수 없는 기간, 기존 ROAS 기간 참조 오류는 **제공 완료로 보지 않고 오류**로 처리한다. 전체 18개 사례에서 **정상 검증된 선언 없음=미제공**임을 보증할 카탈로그/버전/무결성 계약은 여전히 제안 및 스키마 승인 대상이다. 18×제품별 54개의 빈 레코드를 새로 생성하는 방식은 제안하지 않는다.
4. **배포 등록과 오류 격리, 제안:** 기존 `scripts/current-data.mjs`의 `loadCurrentData()`는 `manifest.metadata`에 등록된 파일을 **전부 읽고 해시 검증**하며, 로더 실패는 Vite의 초기화/빌드까지 전파될 수 있다. 따라서 리뷰 원문/분류 파일을 **현행 필수 metadata에 단순 추가하는 안은 그대로 승인하거나 구현하지 않는다.** 우선 검토안은 **기존 ROAS 필수 로더와 독립된 선택적 리뷰 로딩 경계 및 별도 리뷰 무결성 검증**을 두는 것이다. 리뷰 파일 누락, 해시 불일치, 미검수/분류 보류는 리뷰 조회만 `error`/게시 보류로 처리하고 기존 ROAS 화면, 사례 조회와 KPI를 정상 제공해야 한다. 별도 등록 파일 또는 선택적 manifest, 격리 로더의 구체 구조는 후속 승인 대상이다. 공용 `data/manifest.json`의 metadata 구성 변경이 불가피한 경우에는 **이 격리를 먼저 검증한 뒤** 등록한다. manifest 변경으로 전체 `data_sha256` 및 ROAS 응답 `dataHash`가 달라질 수 있으므로 수치/기존 원천/필터 결과의 불변성과 해시 메타데이터 변경은 구별해 확인한다. 로더/응답/분류 저장소의 승인 없는 파일 생성 및 기존 원시 계약 확장은 금지한다.

## 6. 상위 카테고리, 세부 경험과 분류 규약, **세부 인터뷰 B안 확정**

**2026-11-03 SDD 인터뷰 확정(B안): 상위 카테고리 5개(향, 세정 및 사용감, 용기와 포장, 용량 안내, 배송)는 유지하고, 세부 경험은 원문에서 새로운 유형이 확인될 때 별도 검수와 승인 절차를 거쳐 확장한다.** 세부 경험 목록의 최초 후보는 고정된 최종 목록이 아니며 새 유형을 자동 생성하거나 승인 전 집계에 반영하지 않는다. 복수 분류, 근거 없는 강제 분류 금지, 상위 건수/비율과 세부 건수는 최신 Intent의 확정 요구사항이다. 아래 영문 코드, 초기 세부 경험 이름, 저장 구조는 여전히 **계약 제안, 승인 전**이다.

| 상위 코드(제안), 유지할 상위 표시명 | 최초 세부 경험 코드/표시명 후보(확장 가능) | 원문 검수 경계 |
| --- | --- | --- |
| `scent`, 향 | `mild_scent_satisfied` 은은한 향 만족, `strong_scent_disliked` 향이 너무 강함 | 향에 관한 구체 평가가 있는 경우만 |
| `cleansing_feel`, 세정 및 사용감 | `cleansing_satisfied` 세정 만족, `dry_feel_disliked` 사용 후 건조감 불만 | 사용감과 향은 별개 카테고리 |
| `container_packaging`, 용기와 포장 | `container_convenient` 용기 사용 편리, `leakage_reported` 누수 경험 | 외관만 언급한 리뷰를 누수로 추정하지 않음 |
| `volume_info`, 용량 안내 | `volume_info_clear` 용량 안내 명확, `volume_info_confusing` 용량 안내 혼란 | 실제 용량 부족 판정을 임의로 부여하지 않음 |
| `delivery`, 배송 | `delivery_smooth` 배송 과정 만족, `delivery_delayed` 배송 지연 불만 | 배송 언급과 상품 자체의 세정 효과를 연결하지 않음 |

- 하나의 `reviewId`는 **여러 상위 카테고리**와 여러 세부 경험에 포함될 수 있다. 같은 상위 안에 상반된 세부 경험이 공존해도 원문 근거가 각각 있다면 허용한다.
- **분류의 최소 단위**는 `(reviewId, categoryId, experienceId, evidenceQuote)`로 제안한다. `evidenceQuote`는 실제 `text`의 연속 부분 문자열이어야 한다. 반복 표현의 위치가 모호하면 원문 범위를 나타내는 인덱스와 검증 규약을 추가 승인한다. 별점 1~5는 분류 근거를 대신하지 못한다.
- 검수 결과 특정 상위 카테고리를 뒷받침할 근거가 없으면 분류 배열 `[]`로 남기는 **미분류**를 허용한다. 검수 전 `pending`과 검수 완료 후 **근거 없음 `unclassified`**은 구별한다. `pending`을 조용히 미분류로 바꾸지 않는다.
- **세부 경험 확장 절차(B안 확정):** 원문에서 상위 5개 중 하나에 속하지만 기존 세부 코드로 표현하기 어려운 경험이 발견되면, 근거 원문과 후보 명칭을 **별도 데이터 검수**에 등록한다. 유사/중복 코드 여부와 부모 상위 카테고리를 대조하고 사용자 승인 후 세부 코드를 사전에 추가한다. 승인 전에는 임의 코드를 부여하거나 기존 세부 경험으로 강제 매핑하지 않는다. 상위 측면의 근거는 있지만 세부 코드가 없는 건을 **'근거 없음' 미분류로 자동 처리하지 않고 분류 보류**한다.
- **변경 영향:** 세부 경험 추가 시 사전 버전을 갱신하고 기존 리뷰의 재분류 필요성을 검토한다. 영향받는 상위/세부 건수, 비율, 원문 ID를 다시 검산하며 원시 리뷰 48건 자체는 늘리거나 고치지 않는다. 기존 분류 코드의 의미를 조용히 바꾸거나 과거 비교값을 새 분류와 섞어 표시하지 않는다. 구체적 버전 저장 필드와 운영 권한은 아직 신규 계약 승인 대상이다.
- 같은 리뷰에 같은 `experienceId`를 두 번 달거나 상위 카테고리만 세부 경험 없이 확정하는 정책은 **이 초안에서는 금지**한다. 분류 시 실제 근거가 있는 세부 경험과 그 부모 상위를 함께 결정한다. 분류 사전의 버전 변경 시 재검수 범위를 명시한다.
- **대시보드는 읽기 전용**이다. 오류 발견 후 교정은 §9의 별도 검수 절차에서 원시 원문과 구분된 분류 결과를 수정, 검산한 뒤 배포한다. 화면에 검수 상태나 분류를 고객 사실/인과 정답으로 표시하지 않는다.

## 7. 집계와 독립 검산 계약

**공통 필터:** 유효한 `caseId` + 고정 `productId=EDU-P1` + `sourceId`(전체 또는 정확한 출처) + `asOf` + `writtenAt`이 포함된 기간. 캠페인/매체/기기 범위는 리뷰 분모나 선택에 절대 적용하지 않는다. ROAS는 기존의 캠페인/기기 필터를 그대로 따른다.

각 집단 `G(caseId, sourceId, periodId, asOf)`를 **(중복 없는 원문 ID, 작성기간, 보고 기준까지 수집 완료)**로 먼저 만든다.

| 지표 | 수식 및 정합성 |
| --- | --- |
| 전체 표본 `N` | `countDistinct(review.id in G)`. 미분류 포함, 한 리뷰는 한 번만. 제공된 범위 내 0건이면 0. |
| 상위 건수 `n_c` | `countDistinct(review.id in G with category c)`. 복수 세부 경험이 같은 상위에 있으면 1건. |
| 상위 비율 `p_c` | `n_c / N × 100`(%). `N=0`이면 **null/계산 불가**, `N>0, n_c=0`이면 0%. 분모는 미분류까지 포함한 전체 `N`. 카테고리 비율 합계는 **100% 초과 가능**, 100%로 정규화 금지. |
| 세부 경험 건수 `n_e` | `countDistinct(review.id in G with experience e)`. 카테고리 내 세부 합계가 상위 건수보다 클 수 있다. 세부 경험 **비율과 비율 변화는 이번 필수 산출물이 아님**. |
| 미분류 건수 `n_u` | `countDistinct(review.id in G with QA completed and 0 validated assignments)`. 그 리뷰도 전체 원문/표본에 남는다. 미검수는 `n_u`가 아니라 품질 오류/보류. |
| 평균 별점 | `Σ rating / N`(같은 G의 원문만). `N=0`이면 null, 0점 대체 금지. 전체 평균은 출처별 평균의 단순 평균 금지. |
| 기간 차이 | `Δ건수 = current - baseline`, `Δ상위 비율(%p) = p_current - p_baseline`, `Δ평균 별점 = avg_current - avg_baseline`. 어느 쪽이라도 `null`이면 해당 차이도 `null`; 표시는 원값 계산 이후 반올림(권고: 비율 소수 첫째 자리), 검산은 반올림 전 값으로 수행. |

**교차 검산은 적용 범위를 나눈다.** **원천 전체 검산**(S16/S17 × 자사몰/외부 × 두 기간, 추가 목록 필터 적용 전): ① 각 사례의 각 기간 `N=12`, ② 두 사례를 합친 기간별 `N=24`, ③ 두 기간 합계 `48`, ④ 한 사례의 전체 기간 `24`, ⑤ 각 출처의 두 사례, 두 기간 합계 `24`. **조회 필터 검산**: 선택 사례와 기간별 `N(all)=N(own_store)+N(virtual_external_1)`, 선택 출처 `N`은 해당 출처의 원천 셀 수 이하이며, 선택 집합에 필터가 적용되었다면 무조건 `N=24` 또는 `48`을 강제하지 않는다. 예를 들어 **두 사례 + 자사몰만** 선택할 수 있는 검산 범위라면 기간별 `12`, 두 기간 총 `24`이며, 단일 S16 + 자사몰은 각 기간 `4,8`, 두 기간 총 `12`다. 모든 집합에 대해 `0 ≤ n_c ≤ N`, `0 ≤ n_e ≤ n_c`(부모 상위에 한해), `0 ≤ n_u ≤ N`, 중복 없는 원문 ID 및 카테고리별 원문 참조 정합성을 적용한다. **카테고리 총합 = N**과 **세부 경험 합계 = 상위 건수**를 강제하지 않는다.

원문은 안정적으로 `writtenAt` 내림차순, 동일 시각이면 `id` 오름차순으로 반환하는 **데이터 계약 제안**이며 표시 분량/탐색 UX는 UI/UX SDD에서 정한다. **기간별 집계의 `reviewIds`는 동일한 기간/출처/보고 기준으로 조회한 원문 ID 집합과 대조**한다. 단일 응답의 `reviewItems`가 `listPeriod`에 따라 제한된다면 **두 기간 집계의 모든 ID가 그 한 응답의 `reviewItems` 안에 있어야 한다고 검사하지 않는다**. 비교기간/분석기간에 맞춰 별도 원문 목록을 조회하거나 전 기간 원문 목록을 제공하는 구체 설계는 추가 인터페이스 승인 전 미정이다.

## 8. 자료 상태 판정과 UI 제공 인터페이스, **추가 계약 제안**

**자료 제공 상태와 필터 결과는 별개다.** 로더가 파일, SHA, 스키마, 전체 사례 카탈로그, 4개 제공 선언을 정상 검증한 경우에만 다음 규칙을 적용한다.

| 상태(가칭) | 데이터 판정 | 반환 원칙 |
| --- | --- | --- |
| `not_provided` | 선택 사례/상품에 적격 제공 선언이 없음. S01~S15, S18의 EDU-P1 및 모든 EDU-P2/P3 | 건수, 비율을 **0으로 꾸미지 않고**, 해당 기간/판매처에 제공된 자료가 없음을 표시할 정보 제공. |
| `provided` | 제공 선언이 있고 선택 작성기간/판매처에서 `N>0`, 보고 기준까지 확보 | `N`, 집계, 원문과 대상 기간/보고 기준, 출처 공개. |
| `provided_empty` | 제공 선언은 유효하지만 선택 작성기간에서 보고 기준까지 수집된 적격 원문 `N=0` | `N=0`, 평균/상위 비율 `null`, 원문 `[]`. **표본 내 0건**임을 표시. |
| `error` | 파일 없음/읽기 실패/해시 불일치/파싱 오류/잘못된 조회 범위/제공 선언 불완전/원문, 분류 무결성 실패 | 오류코드와 재시도 가능 여부, 정상 자료로 오인시키지 않는 메시지. 기존 ROAS KPI 제공은 지속. |

다음은 **저장된 원본 스키마가 아닌 읽기 전용 조회 DTO의 제안**이다. 필드명, API URL, 캐시 정책, 배포 경로는 승인 전 미정이다.

```text
ReviewQuery {
  caseId: "S01".."S18",
  productId: "EDU-P1",             // 이번 리뷰 UI에선 고정, 별도 상품 선택 없음
  snapshotId: "initial"|"mature", // 기존 ROAS 보고 기준과 동일
  sourceId: "all"|<승인된 판매처 ID>,
  listPeriod: "baseline"|"current"|"both" // 원문 목록용, 두 기간 집계는 항상 반환
}
ReviewView {
  contract: <신규 조회 계약, 제안>,
  caseId, productId, asOf, dataHash, classificationVersion,
  appliedScope: {reviewBy: "product_source", roasFiltersApplied: false},
  caseAvailability: "not_provided"|"provided"|"error", // 사례×상품의 제공 선언 상태, 제안
  selectionStatus: "provided"|"provided_empty"|"not_provided"|"error", // 선택된 목록 범위 상태, 제안
  coverage: <제공 선언/작성기간/보고 기준/상태>,
  periods: [{periodId, start, endExclusive, N, meanRating,
             categories:[{categoryId, count, percent, reviewIds}],
             experiences:[{experienceId, categoryId, count, reviewIds}],
             unclassifiedCount, unclassifiedReviewIds}],
  reviewItems: [{id, writtenAt, collectedAt, sourceId, sourceName,
                 rating, ratingScale, text, categories, experiences}],
  error: <오류 상태에서만 오류코드>
}
```

- `periods`는 비교/분석 **두 기간 모두** 제공해 판매처 변경 때 같은 분모로 재계산하게 한다. `listPeriod`는 원문 목록의 범위에만 관여한다. 원문 목록에만 적용한 제한을 비교표의 표본 분모에 섞지 않는다. **정합성 검사 범위도 기간별로 분리**해 `listPeriod=current`일 때는 분석기간 원문만 `reviewItems`에 포함되어도 비교기간 집계가 정상이다. 비교기간 `reviewIds`는 `listPeriod=baseline` 또는 `both`의 조회로 역참조할 수 있어야 한다. **같은 응답에 모든 원문을 담는 방식 vs 기간별 조회 방식은 별도 계약 승인 대기**이며 한 응답에 없는 ID를 무결성 오류로 단정하지 않는다.
- `caseAvailability`는 요청한 목록 범위의 `selectionStatus`와 구분해 **사례×상품별 제공 여부**도 조회할 수 있어야 한다. **현 `ReviewQuery.productId`는 EDU-P1만 허용하므로 이 조회 자체로 EDU-P2/P3을 요청하거나 미제공을 반환할 수 없다.** 후속 인터페이스 승인에서 **별도 읽기 전용 제공상태 카탈로그**(모든 S01~S18의 EDU-P1~P3에 대한 제공/미제공, 유효한 전체 coverage 기준) 또는 상품별 상태 조회를 분명히 선택해야 한다. 이번 UI는 상품 1 전용으로 유지하고 상품 선택 기능을 추가하지 않는다. 원시 리뷰 조회 오류를 임의로 미제공으로 덮지 않는다.
- `classificationVersion`과 `dataHash`가 집계/원문과 같은 스냅샷인지 확인한다. 분류가 미검수 또는 계약 오류라면 부정확한 카테고리 집계를 조용히 표시하지 않고 오류/보류로 드러낸다.
- `roasFiltersApplied=false`는 **리뷰만** 캠페인/기기 필터와 무관하다는 뜻이다. ROAS는 그 필터에 따라 달라질 수 있으며 리뷰와 동일 고객군 또는 광고의 직접 반응으로 해석할 수 없다.
- `provided_empty`는 선택한 **작성기간과 보고 기준**에서만 0건임을 뜻하고, 수집일로 기간을 다시 나눠 계산한 0건과 혼동하지 않는다.
- 제품 선택 UI, 자유 키워드 검색, 분류 편집 API, Agent1 자동 분석 응답과 임의 인과 요약을 이 인터페이스에 넣지 않는다. 읽기 전용 제공과 원문 검증에 필요한 관계만 담는다.

## 9. 분류 오류 검수, 결과 반영 및 감사 절차, **인터뷰 3 B안, 인터뷰 4 A안 확정, 세부 기록 계약 검토 중**

**2026-11-03 SDD 인터뷰 3 확정(B안): 원문 48건 모두를 1차 담당자가 분류하고, 1차 담당자와 다른 2차 검수자가 48건 전부에 대해 원문과 분류 근거를 대조한다.** 이는 서로 다른 두 사람이 48건을 각각 처음부터 독립적으로 분류하는 A안과 다르며, 일부 중요 리뷰만 집중 검수하고 나머지를 표본 검사하는 C안도 아니다. **검수 단위는 48개 고유 리뷰 ID 전부**이며 S16과 S17 각 24건을 포함한다. **인터뷰 4 A안 확정:** 이견은 먼저 1차/2차 담당자가 원문 근거를 놓고 협의하며, 합의되지 않은 건만 1차/2차와 다른 제3 검수자가 최종 판정한다. 검수자 실명, 선정 기준과 실제 QA 기록 필드는 미확정이다. 계약/집계의 독립 검산 담당 역할은 별도 제안으로 유지한다.

1. **원문 품질 입고:** 48개 원문의 ID, 소속, 판매처, 작성/수집 일시, 별점, 금지 링크, 합성 표본 고지 여부를 확인한다. **§4.1에 따라 전수 원문 고유성 및 1,128쌍의 텍스트/의미 유사 후보를 대조하고, 의미상 중복 후보별 검토 결과와 구별 근거를 남긴다.** 원시 파일 해시와 기존 ROAS 보존 기준 해시를 기록한다.
2. **1차 48건 전수 분류, 확정:** 한 담당자가 S16 24건과 S17 24건의 원문 ID를 빠짐없이 확인한다. 각 리뷰에 상위/세부 경험 0개 이상, 복수 분류와 증거 인용 또는 근거 부족/미등록 경험에 따른 보류 사유를 기록한다. 강제 긍정/부정, 별점 대체 추론, 근거 없는 강제 분류를 금지한다. 1차에서 비어 있는 분류는 바로 검수 완료로 간주하지 않고 2차 확인을 거친다.
3. **2차 48건 전수 검수, 확정:** **1차 담당자와 다른 사람**이 48개 원문 ID 각각을 직접 열어 원문과 할당 결과를 대조하고, §4.1의 **문구 복제/의미상 중복 후보와 원문별 구별 근거**도 확인한다. 인용의 실제 존재와 의미, 부모–세부 경험 관계, 복수 분류의 누락/과잉, 미분류 근거의 적합성, 새 경험 보류의 타당성 및 S16/S17별 A/B/C 증거를 점검한다. **1차 기록 48건, 2차 확인 48건의 ID 집합이 각각 원문 48개 ID 집합과 정확히 일치**해야 한다. 2차는 1차 결과를 검증하는 절차이며 별도의 독립 최초 분류 48건을 추가 작성할 의무는 아니다. 불일치는 확정 분류로 덮어쓰지 않고 이견 건으로 보류한다.
4. **이견 해결, 인터뷰 4 A안 확정:** 이견이 생기면 **1차와 2차 검수자가 해당 원문과 사전의 의미를 대조해 먼저 협의**한다. 두 검수자가 합의하면 그 근거와 결론을 별도 검수 결과에 기록한다. **합의가 없으면 1차/2차와 다른 제3 검수자가 원문과 양측 근거를 확인해 최종 판정**한다. 이견이 열린 상태이거나 제3자 판정을 받지 못하면 해당 분류는 승인되지 않으며 영향받는 집계의 검증/공개를 보류한다. 최종 판정이 '근거 부족'인 경우에도 의미를 추정해 분류하지 않는다. 신규 세부 경험의 사전 확장은 인터뷰 1의 **별도 승인 절차**를 따라야 하며 제3자 판정만으로 신규 코드를 자동 추가할 수 없다.
5. **교정:** 원문 오기와 분류 오류를 구별한다. **인터뷰 2 B안에 따라 분류 오류는 원문과 분리된 분류 결과 파일에서만 교정**하고, 별도 검수 이력에 근거, 이전 값, 변경 값, 검수자, 일시, 버전과 승인을 기록하도록 제안한다. 영향받는 모든 집계는 재계산하며 원문 ID, 원문 파일 내용과 해시는 유지해야 한다. 원문 자체의 오기 수정이나 신규 관측 추가가 필요하다면 분류 교정과 혼합하지 않고 기존 승인 범위 및 [데이터 변경 승인 규칙](../../AGENTS.md)을 따로 확인한다.
6. **재검산 및 공개:** 원시 해시와 분류 버전, 4개 선언, 8개 사례×기간×판매처 셀의 정수 합계, 상위/세부 ID 집합, 빈 상태를 독립 계산과 대조한다. 통과한 읽기 전용 파생 자료만 공개한다. 수정 전후 분류와 검증 결과는 감사 가능하게 보존한다.

**인터뷰 3, 4 인수 게이트:** 48개 리뷰 ID 모두에 1차 분류 기록과 **다른 검수자의 2차 원문 대조 완료 기록**이 있어야 한다. 이견이 없다면 2차 확인 결과로 완료, 이견이 있다면 **양측 협의 결론 또는 미합의 건의 제3자 최종 판정**이 반드시 있어야 완료다. 의견이 남아 있거나 제3자 확인 없이 일방적으로 확정한 건, 누락/중복 기록, 근거 없는 인용, 단순 보류를 미분류로 취급한 건은 통과할 수 없다. 합의/제3자 판정 경로와 최종 근거를 대조해 이견 0건인 상태에서만 분류 집계 게시 승인을 제안한다. 감사용 담당자, 검수 시각, 합의/제3자 경로, 이전/최종 값, 판정 근거의 **구체 필드 및 저장 구조는 신규 스키마 승인 대상**이다.

**분류되지 않음 ≠ 부정 경험 없음.** 분류 오류가 발견돼도 마케터 화면에서 직접 고치는 대신 별도 검수 결과를 반영하며, 현재 대시보드 사용자가 확인하는 것은 분류 상태와 근거 원문뿐이다.

**인수 보류 조건:** 완전 중복 원문 또는 차별화 근거 없는 의미상 중복의 미해결 건, 원문 48건의 다양성 검수 누락, 근거 없는 강제 분류, 미검수를 미분류로 대체, 전 사례 상품 정의 누락, 보고 기준 이후 자료 소급, 출처 가중치 없는 추세 판단, 미제공과 0건/오류 혼동, **기간별 집계에 대한 원문 참조 실패**, **리뷰 오류가 ROAS 조회/빌드를 막는 경우**, 원시 ROAS 수치 재생성 또는 기존 상품 2/3 변경 중 하나라도 발생하면 데이터 SDD의 성공으로 선언하지 않는다.

**자체 검토 상태 (2026-11-03):** 최신 Intent의 48건/4개 제공 선언, 전 사례 EDU-P1 샴푸, 작성일/수집일 분리, S16, S17별 A/B/C, 복수 분류/미분류, 상위 건수, 비율/세부 건수, 세 상태 구분, 데이터 검수 분리, 기존 ROAS 불변 및 승인 게이트를 위 인수 조건에 연결했다. 부호 0을 B 사례 합격으로 오인하지 않도록 엄격한 반대 방향 판정을 지정했다. **데이터 생성, 코드, 테스트 변경, 테스트 실행, UI/UX SDD 수정, 커밋/푸시는 수행하지 않는다.**

## 12. SDD 구체화, 계약 후보와 결정 근거 (intent-to-done 2단계)

이 절은 최신 Intent가 요구한 결과를 **구현자가 계약과 예외로 옮길 수 있도록 하는 구체화안**이다. 아래 `제안` 필드는 기존 `roas-training/1` 또는 이미 승인된 `roas-reviews/1`에 존재하는 필드가 아니며, **계약 검토와 별도 승인 전에는 저장, 배포하거나 입력을 생성하지 않는다.** 실제 리뷰 예문, 별점 또는 분류 정답은 이 문서에 생성하지 않는다.

### 12.1 원시 계약별 고정값과 참조, 제안

| 범위 | 제안할 결정 | 이유와 호환성 경계 |
| --- | --- | --- |
| 사례 카탈로그 | 기존 `trainingCaseIds`에 등록된 S01~S18을 유일한 대상 집합으로 사용 | 신규 사례 ID 생성 없이 미제공을 전 사례에 표현 |
| 교육용 상품 의미 | **인터뷰 5 A안 확정:** 원본 상품 구조/파일과 분리한 **공통 상품 메타데이터 파일 하나**에서 EDU-P1의 샴푸 품목을 한 번 정의해 S01~S18 공통 참조. `EDU-P1: categoryName="샴푸"`는 **필드명/표현의 후보** | EDU-P1의 기존 ID, `products[].label`, 정가, 사례별 ROAS 값과 EDU-P2/P3 정의 불변. 공통 참조의 검증과 상품 파일 누락 시 리뷰 영역 오류 격리 필요. 정확한 메타데이터 계약/등록은 승인 대기 |
| 판매처 코드 | `own_store`(자사몰), `virtual_external_1`(가상 외부 판매처)의 **두 고정 enum 후보** | 문자열 오타와 판매처 중복을 막고 리뷰가 실제 사이트를 가리키지 않도록 함. 정확한 코드와 표시명은 승인 대기 |
| coverage 행 | **인터뷰 6 A안 확정:** `caseId`, `productId`, `sourceId`가 가리키는 **4개 제공 선언 각각**에 `periodIds: ["baseline", "current"]` 명시. 필드 의미와 필수성은 확정, 최종 파일 스키마/계약명은 승인 대기 | 기간별 8개 선언으로 부풀리지 않고 4개 유지. 각 기간의 시작/끝은 해당 사례의 ROAS `periods`에서 참조, 기간 날짜 중복 저장 금지. 누락/중복/유효하지 않은 기간 코드 오류 판정 |
| 분류 참조 | **인터뷰 2 B안 확정:** 원문 파일과 분류 파일을 물리적으로 분리, 원문 `reviews[].id`를 분류 `reviewId`로 참조, 원문 본문/별점/작성일/수집일/상품/판매처/기간은 분류 파일에 복제하지 않음 | 분류 수정으로 원문 48건이나 ROAS 값이 바뀌지 않도록 분리. ID 정합성, 원문 해시 및 분류 버전 검증 필드의 구체 스키마는 후속 승인 |
| 자산 해시 | 원문 해시, 분류 해시, 교육용 상품 의미 해시를 **각각** 관리하고, 공개 파생물에 사용한 버전을 기록 | 원문과 분류의 불일치, 부분 교정된 집계, 과거 ROAS 보존 위반을 탐지 |

**coverage 불변식, 인터뷰 6 A안 확정:** 고유 키 `(caseId,productId,sourceId)`는 정확히 4개이며 `{S16,S17} × {EDU-P1} × {own_store,virtual_external_1}`이다. **각 선언의 `periodIds` 값은 정확히 두 개 `baseline`과 `current`를 각각 한 번씩 포함**한다. 두 기간의 실제 날짜는 `trainingScreenData(...,caseId,snapshotId).periods`가 정의하며 선언 안에 별도 날짜를 복제하지 않는다. 검산 시 모든 선언에 두 기간이 존재하고 각 ROAS 기간 ID가 실제로 해석되는지 확인한다. 4개 중 선언 누락, 중복 키, 기간 ID 누락/중복/미등록, ROAS 기간 참조 실패는 `error`이며, **S16 또는 S17 선언 누락을 '미제공'으로 대체하면 안 된다.** 실제 원시 스키마 및 코드/데이터 변경은 별도 승인 전 미실행이다.

### 12.2 별도 분류 파일, 인터뷰 2 B안 확정, 최소 타입은 제안

**2026-11-03 사용자 확정:** 리뷰 원문 파일과 분류 결과 파일을 분리해 저장한다. 원문은 단일 근거이며 분류 파일은 `reviewId`로만 원문을 참조한다. 파일의 위치와 계약 버전, 검수 정보 필드 등은 이 **설계 방향의 승인과 별개로** 세부 계약 승인이 필요하다. 다음은 **새 파일의 스키마 제안**이며 저장된 JSON, 승인된 필드 목록, 실제 리뷰 데이터가 아니다.

```ts
type CategoryId =
  | 'scent' | 'cleansing_feel' | 'container_packaging'
  | 'volume_info' | 'delivery';
type ClassificationStatus = 'pending' | 'classified' | 'unclassified';
type ReviewClassification = {
  reviewId: string; // 원문 리뷰 ID, 48개와 정확히 1:1
  status: ClassificationStatus;
  assignments: Array<{
    categoryId: CategoryId;
    experienceId: string;    // 승인된 사전에서 categoryId 아래에만 존재
    evidenceQuote: string;   // 원문 text의 연속 부분 문자열
  }>;
};
type ClassificationBundle = {
  contract: 'roas-review-classifications/1'; // 신규 계약 후보
  sourceReviewSha256: string;
  taxonomyVersion: string;
  results: ReviewClassification[];
};
```

- `results`는 원문 48개 ID와 집합 동등이고 원문당 **정확히 한 상태**다. 리뷰 한 건의 복수 할당은 `assignments[]` 안에 기록한다. 인용된 근거는 원문과 문자 단위로 대조하되 인용이 증명하지 않는 의미를 덧붙이지 않는다.
- `status=classified`면 할당 1개 이상, `status=unclassified`면 할당 0개와 **검수 완료 근거**, `status=pending`이면 배포 전 보류다. `pending`을 전체 분모에서 빼거나 `unclassified`로 오인하지 않는다. 충분한 평가 측면을 찾지 못한 원문은 삭제하지 않는다.
- **상위 5개는 유지하고 세부 경험만 검수/승인 후 확장**한다(B안 확정). 세부 경험 사전은 **각 승인 버전 안에서만 닫힌 목록**이고, 버전 사이에는 승인된 경험 추가가 가능하다. 검수된 `assignments`는 해당 버전에 존재하는 `experienceId`만 가리키고 그 부모는 `categoryId`와 같아야 한다. 새 코드 후보는 검수/승인 전 매핑, 집계, 배포에서 제외하며 해당 원문은 강제 미분류하지 않고 분류 보류한다. 동일한 `(reviewId, experienceId)` 중복 할당 불가.
- 개별 수정자의 식별, 검수 근거, 이전/이후 분류, 교정 사유, 승인 시점은 **공개 자료가 아닌 내부 QA 변경 이력**으로 별도 관리하도록 제안한다. 이력의 필드명, 관리 주체와 저장 위치는 승인 전 미정이다.
- **선택 근거(인터뷰 2 B안 확정):** 분류를 원문 `reviews[]`에 내장하면 분류 수정만으로 원문 팩과 해시가 달라지는 문제가 있다. **별도 파일 방식을 채택**해 원문과 분류의 변경 이력을 구별하고, 대시보드 조회는 검수 완료된 분류 버전만 참조한다. 반대로 파일 간 ID와 원문 해시가 맞지 않거나 분류 버전이 서로 다르면 정상 집계를 제공하지 않는다. **분류 파일의 후보 경로/필드명/배포 접근 정책은 여전히 설계 제안**이다.

### 12.3 판정 순서와 예외별 결과, 제안

정상/실패 분기의 판정 **순서가 의미를 바꾼다**. 리뷰 요청을 받을 때 (1) 정해진 사례, `EDU-P1`, 기간, 스냅샷 및 판매처 유효성 검사 → (2) 원문, 분류, 제품 메타데이터와 manifest 무결성 검사 → (3) 전체 제공 선언 4개 완전성 확인 → (4) 요청 사례의 제공 여부 확인 → (5) 작성기간 귀속과 수집일 보고 제한 후 분모 계산 → (6) 검수 완료 분류로 집계 → (7) 원문과 집계 ID 집합을 일치시켜 반환한다.

| 입력/조건 | 사례 자체의 제공 상태 | 선택 범위 결과 | 판정 |
| --- | --- | --- | --- |
| S01~S15 또는 S18의 EDU-P1, 정상 로드 | `not_provided` | 수치 및 평균 `null` | 리뷰 부재가 아니라 **제공 자료 없음** |
| S16/S17의 EDU-P1, 정상 로드, 기간에 적격 원문 존재 | `provided` | `provided`, 건수와 비율 계산 | 두 기간 비교와 원문을 같은 필터로 검산 |
| 제공 선언이 있으나 선택 작성기간/판매처/보고 기준의 적격 원문이 0개 | `provided` | `provided_empty`, 건수 `0`, 평균과 비율 `null` | **선택 결과만** 0건, 자료 자체는 제공 상태 |
| 원문/분류 파일 읽기 실패, SHA/스키마 오류, S16/S17 선언 유실 | 판정 불가 | `error` | '미제공'이나 '0건'으로 자동 전환 금지 |
| 알 수 없는 사례, 출처 또는 스냅샷 | 판정 불가 | `error` + `invalid_request` | 잘못된 요청으로서 데이터 부재와 분리, 재시도로 자동 해결된다고 표시하지 않음 |
| 분류 미검수나 원문–분류 해시 불일치 | 원문 제공 여부는 별도 확인 가능 | 분류 집계 `error` 또는 게시 보류 | 근거 없는 카테고리 비율을 정상값으로 표시하지 않음 |

**상태의 두 층:** `caseAvailability`는 이 사례의 **제공 선언 존재 여부**, `selectionStatus`는 해당 `listPeriod`, 판매처와 `asOf` 필터 결과를 뜻하도록 조회 DTO를 구체화한다. 둘을 하나의 `availability`에 합치면 S16의 기간 0건을 '전체 미제공'으로 잘못 보일 수 있다. **기존 §8 DTO의 단일 `availability`는 이 이중 판정으로 변경하자는 제안**이며 확정 API가 아니다. `listPeriod`가 바뀌어도 `periods[]`의 두 기간 집계는 그대로 반환한다. 모든 상품의 상태 확인은 현 `ReviewQuery.productId=EDU-P1`로 할 수 없으므로 **별도 제공상태 카탈로그 또는 상태 전용 조회**를 반드시 설계해야 한다. 검수 전 임시로 P2/P3을 선택 가능한 리뷰 상품으로 노출하지 않는다.

**오류 격리 선행 조건, 제안:** 리뷰 로더, 리뷰 해시 검사, 분류 검수 상태 판정은 ROAS 필수 데이터 로드에 실패를 전파하지 않는 별도 경계에서 실행해야 한다. 현재 `scripts/current-data.mjs`의 필수 metadata 일괄 검증 경로에 신규 리뷰 파일을 그냥 등록하면 앱 부팅/빌드도 실패할 수 있으므로 **등록 전에 격리 시나리오 인수 테스트**를 승인받아야 한다. 이 실패에서 리뷰는 `error`/게시 보류이지만 기존 ROAS 화면과 사례별 KPI는 정상 유지되어야 한다. `dataHash` 변경 가능성은 수치 보존 위반과 구분한다.

### 12.4 조회 원문/집계의 동일성, 정렬과 정확도

- 집계 단계에서 `(caseId, productId, sourceId, periodId, asOf)`에 해당하는 **필터된 리뷰 ID 집합**을 유일한 모집단으로 정한다. 평균과 상위/세부 건수, 미분류 수, 카테고리 원문 링크는 **같은 ID 집합**에서 계산한다.
- `all` 판매처의 `N`은 두 판매처 `N`의 합이다. 다만 상위 건수는 원문 ID를 합집합으로 계산하므로 외부 출처와 자사몰 ID가 겹치면 그 자체가 원본 ID 무결성 오류다.
- 사용자에게 제공할 건수는 **정수 원값**, 비율은 산출 원값을 유지하고 표시에만 반올림한다. `N=0`에서 평균, 비율, %p 변화는 `null`이다. `0/0=0`을 허용하지 않는다.
- 정렬 제안은 `writtenAt DESC, id ASC`. 동일 시각, 동일 ID는 중복 오류이므로 안정 정렬만으로 숨기지 않는다. **각 기간의 집계 `reviewIds`는 같은 작성기간과 출처, 보고 기준으로 접근 가능한 원문 ID 집합에 역참조**되어야 한다. `listPeriod=current`로 좁힌 한 응답의 `reviewItems`에 비교기간 ID까지 요구하지 않는다. 비교기간 원문을 `listPeriod=baseline`/`both`로 가져오는 방식과 두 기간 원문을 한 번에 반환하는 방식 중 어떤 인터페이스로 확정할지는 후속 승인 대상이다.
- 각 스냅샷에서 승인된 48건은 모두 `initial` 보고 기준 전에 확보되는 조건이므로, `initial`와 `mature`의 원문 ID 집합과 분류 집합이 **동일**해야 한다. ROAS의 후속 전환 지연 집계가 바뀔 수 있다는 사실을 리뷰 갱신 근거로 삼지 않는다.

## 13. intent-to-done 인계 계획, 위험과 완료 판정

**현재 위치:** 단계 0 현황 확인, 단계 1 최신 Intent 확정 근거 대조, **단계 2 SDD 세부 인터뷰 진행 중**. 2026-11-03 사용자 지시에 따라 **데이터 품질과 유사 리뷰 최소화에 집중**하며, **화면 제공 방식 관련 인터뷰 7은 미확정으로 별도 UI/UX SDD에 이관**한다. **인터뷰 1 B안**(상위 5개 유지, 세부 경험 검수/승인 후 확장), **인터뷰 2 B안**(원문과 분류 결과 별도 파일 저장), **인터뷰 3 B안**(1차 48건 전수 분류와 다른 검수자의 2차 48건 전수 원문 대조), **인터뷰 4 A안**(1차/2차 협의 후 미합의만 제3자 최종 판정), **인터뷰 5 A안**(EDU-P1 샴푸 품목을 별도 공통 상품 메타데이터 파일에 한 번 정의), **인터뷰 6 A안**(coverage 4건 각 `baseline`/`current` 기간 ID 명시)은 사용자 확정이다. 세부 분류 코드, 파일 경로/필드와 QA 감사 기록 세부 구조는 아직 승인 대기다. 단계 3 TDD부터는 **아직 미착수**다. **2026-11-03 병렬 설계 검수 5건 반영 현황:** 중요 ① §7, §8, §12.4에서 `listPeriod`로 제한된 한 원문 목록과 두 기간 집계의 `reviewIds`를 잘못 대조하는 조건을 제거하고 **기간별 원문 접근성**을 인수 조건으로 명시했다. **전체 원문 동시 제공 vs 기간별 조회 방식은 미결**이다. 중요 ② §5.2, §10 DATA-08/12, §12.3, §13 P4에서 **기존 필수 metadata 일괄 로더와 리뷰 오류 격리 필요성**을 명시했다. **격리 로더/등록 구조는 승인 대기**다. 경미 ③ §7에서 전체 원천 수량과 필터별 수량 검사를 분리, ④ §5.2/§13에서 원천, 성과 수치 불변과 전체 manifest `data_sha256`/ROAS 응답 `dataHash`의 예상 변경을 분리, ⑤ §8/§12.3/§11에서 EDU-P1 전용 리뷰 요청과 EDU-P2/P3 제공상태 확인의 계약 경계를 분리했다. **상품별 상태 카탈로그 경로는 승인 대기**다. 이 수정은 설계 문서에만 반영했으며 **검수 지적의 실행 통과를 의미하지 않는다.**

**자체 검토 게이트:** **2026-11-03 사용자 추가 품질 중점(48건 의미 다양성, 복제 리뷰 최소화)은 요구사항으로 반영했으나 원문 검수는 미실행**이다. 인터뷰 1의 상위 5개 유지/세부 확장, 인터뷰 2의 원문/분류 별도 파일 저장, 인터뷰 3의 1차/2차 48건 전수 대조, 인터뷰 4의 **양자 협의 후 미합의 제3자 판정**, 인터뷰 5의 **별도 공통 상품 메타데이터 파일**, 인터뷰 6의 **4개 coverage 선언마다 두 작성기간 ID 명시**는 `사용자 확정`, 파일 경로/계약명, 상품 메타데이터 스키마, QA 기록 필드, 실제 검수자 배정과 세부 운영안은 `제안/승인 대기`, 실제 리뷰 데이터와 A/B/C 지표의 값은 `미생성`, TDD, 실행, 시각 UI의 사용자 테스트는 `미실행`으로 남긴다. 스펙 수용과 데이터/코드 생성 승인을 분리한다. 실제 리뷰가 없으므로 A/B/C 적합성 및 공개된 조회 상태의 실행 통과는 **아직 주장하지 않는다**.
