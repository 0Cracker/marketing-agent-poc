### 2026-11-02 후속 Intent 확정, 리뷰 분석 적합성

이 절은 후속 인터뷰에서 사용자가 직접 확정한 내용만 기록한다. 데이터 생성 Intent와 UI/UX Intent를 분리하며, 기존 SDD 문서는 승인 전 초안으로 유지한다.

- 리뷰 영역의 목적: 원문과 기간별, 판매처별 변화를 비교하고 ROAS 조사에서 확인할 근거로 활용한다. 원문만 읽을 수 있는 것으로 목표 달성을 선언하지 않는다.
- 데이터의 성공 목표: 데이터 수량, 형식의 정합성뿐 아니라 **Agent1이 상반된 리뷰 근거를 비교할 수 있는 분석 적합성**을 확인한다. 이것이 실제 모델의 성능 평가 완료를 뜻하지는 않는다.
- 필수 분석 상황 A: **같은 제품, 같은 기간, 같은 평가 측면에 대한 상반된 고객 경험**을 포함한다. 한쪽 리뷰만 택하거나 서로 다른 경험을 논리적 오류로 단정하지 않아야 한다.
- 필수 분석 상황 B: **전체 평점 또는 리뷰 추세와 판매처별 추세의 방향 차이**를 포함한다. 판매처 내부 변화와 표본 구성 변화를 구분할 근거가 필요하다.
- 필수 분석 상황 C: **작성 및 수집 시점과 ROAS 변화의 선후 관계를 잘못 해석하지 않는 시간 순서 검증**을 포함한다. 뒤에 작성된 리뷰가 이전 변화의 원인이었다고 단정하지 않되, 리뷰 작성일이 고객 경험 발생일과 동일하다고도 가정하지 않는다.
- 리뷰 비교기간 판정과 보고 시점 구분(2026-11-03 사용자 확정, A안): **리뷰가 비교기간 또는 분석기간 중 어디에 속하는지는 작성일(`writtenAt`)로 판정**한다. **수집일(`collectedAt`)은 자료가 확보된 시점을 의미하며, 수집 시점이 해당 ROAS 보고 기준 이전인지 확인**하는 용도로 사용한다. 예를 들어 비교기간인 8월 15일 작성, 분석기간인 8월 18일 수집한 리뷰가 보고 기준 이내에 수집되었다면 **비교기간 리뷰**로 계산한다. 작성일과 수집일을 같은 날짜나 같은 의미로 다루지 않으며, 보고 기준 이후에 확보한 리뷰를 과거 보고에 포함하지 않는다. 작성일은 실제 제품 사용일 또는 ROAS 변화의 원인 발생일을 뜻하지 않는다. 기존 승인된 48건과 기간별 배분, 보고 기준은 변경하지 않는다.
- **S16과 S17 각각 A, B, C 전부 필수**이며, 기존 승인된 총 **48건 (각 사례 24건)** 을 유지한다. 다른 상품, 주문, 캠페인과 개별 리뷰를 근거 없이 연결하지 않는다.
- 데이터 생성의 성공 경계(사용자 확정): 승인된 48건의 구조, 대상과 기간 및 출처 관계와 A, B, C의 상반된 근거가 실제 자료에서 검토 가능한지 **독립적인 데이터 분석 적합성 검증까지** 수행한다. Agent1 모델을 실제 호출해 분석 응답의 정답률이나 품질을 채점하는 평가는 **별도 후속 작업**으로 둔다. 데이터 자체의 적합성과 모델의 실제 성능을 혼동하지 않는다.
- UI/UX의 성공 경계(사용자 확정): 마케터가 **같은 성과 현황 화면에서 ROAS와 리뷰를 직접 비교**할 수 있어야 한다. 리뷰의 기간별, 판매처별 변화를 원문과 연결해 검토하고 위쪽 ROAS 변화와 대조하는 것이 목표다. 특정 리뷰를 Agent1에 전달하거나 Agent1이 해당 화면에서 분석 결과를 생성하는 연결 기능은 **후속 작업**으로 분리한다. 같은 화면에 놓았다는 사실만으로 리뷰가 ROAS 변화의 원인임을 뜻하지 않는다.
- UI/UX에서 직접 확인할 수 있어야 하는 상황(사용자 확정): 마케터는 **상반된 평가(A)**, **전체와 판매처별 추세 차이(B)**, **리뷰 작성, 수집 시점과 ROAS 변화의 시간 순서(C)**를 같은 화면에서 스스로 찾아 확인할 수 있어야 한다. 수치를 단순히 나열하는 것만으로 충분하다고 보지 않는다. 자동 해석과 인과 판단은 이 UI의 완료 조건에 넣지 않으며, 어떤 표시 방식으로 탐색을 지원할지는 UI/UX SDD에서 결정한다.
- UI/UX에서 구분해야 할 자료 상태(사용자 확정): **리뷰 자료 미제공**, **자료 제공이 확인된 범위 안에서 선택한 작성기간에 해당하면서 보고 기준까지 확보된 리뷰 0건**, **자료 조회 오류**를 서로 다른 상태로 보여야 한다. 미제공과 조회 실패를 리뷰나 불만이 실제로 없었다는 주장으로 바꾸지 않는다. 표본 안의 0건은 전체 고객이나 전체 판매처의 리뷰가 0건임을 뜻하지 않는다. 작성일 기준 기간 구분과 수집일 기준 보고시점 제한을 혼동하지 않는다. 구체적인 문구, 표시 위치, 재시도 흐름은 UI/UX SDD에서 정한다.
- 모든 ROAS 사례의 리뷰 자료 상태 확인(사용자 확정, A안): **S01~S18 모든 사례에서 리뷰 자료가 제공되는지 직접 확인**할 수 있어야 한다. 이번 승인된 리뷰 원문 48건의 제공 대상은 **S16과 S17의 `EDU-P1`만**이며, **S01~S15와 S18은 '리뷰 자료 미제공'**으로 구분한다. `EDU-P1`의 품목을 모든 사례에서 샴푸로 통일한 사실만으로 다른 사례에 리뷰가 제공된다고 간주하지 않는다. S16/S17의 다른 상품도 리뷰 제공 여부를 그대로 구분하고, '미제공'을 '0건'이나 오류로 대체하지 않는다. 리뷰 제공 여부의 표시 위치와 화면 구성은 UI/UX SDD에서 결정한다.
- 캠페인과 기기 필터 적용 시 비교 정책(사용자 확정, A안): **ROAS는 선택한 캠페인과 기기 범위**를 유지하고, **리뷰는 상품과 판매처 기준으로 계속 제공**한다. 리뷰에 캠페인 또는 기기 필터를 임의로 적용하지 않으며, 두 자료가 동일한 고객 집단을 뜻하지 않는다는 **적용 범위의 차이를 명확히 안내**한다. 마케터가 참고 정보로 나란히 검토할 수 있지만 광고 캠페인별 리뷰나 인과관계로 해석하게 만들지 않는다.
- 상품 선택 UI 범위(2026-11-03 사용자 확정, A안): 이번 리뷰 영역은 **기존 상품 1(`EDU-P1`, 샴푸) 전용**으로 제공하고, **별도의 상품 선택 기능은 만들지 않는다**. S16과 S17에서 제공되는 신규 리뷰 48건은 상품 1만 대상으로 한다. **상품 2, 3의 ROAS 데이터와 기존 분석 표는 유지**하며, **S01~S18 모든 사례에서 리뷰 자료 제공 여부를 확인**할 수 있어야 한다. 리뷰가 없는 다른 사례와 상품은 자료 미제공 상태로 구분한다. 특정 사례에서 리뷰가 제공됐는지의 상태 확인은 상품 선택 UI 없이도 가능해야 한다. 상품 1 전용 영역의 표시 방식과 상태 배치는 이후 UI/UX SDD에서 결정한다.
- 복합 리뷰 탐색(사용자 확정, B안): 리뷰를 단순히 긍정과 부정 두 집단으로 나누는 것만으로는 부족하다. **향, 세정 및 사용감, 용기와 포장, 용량 안내, 배송 등 여러 측면의 복합적인 카테고리**로 탐색하고, 같은 측면에 대한 상반된 평가를 **빠르게 찾아 대조**하며, **근거가 되는 원문도 필요할 때 직접 확인**할 수 있어야 UI/UX가 성공이다. **리뷰 한 건에 여러 평가 측면과 서로 다른 평가가 공존하면, 해당 리뷰를 복수 카테고리에서 찾을 수 있어야 한다(사용자 확정, 복수 분류 B안).** 예를 들어 향은 만족하지만 사용감은 불만인 원문을 '향'과 '사용감' 양쪽에서 찾되 원문은 동일한 리뷰 한 건으로 유지한다. 세부 카테고리 체계, 분류 결과를 데이터에 저장할지 또는 화면에서 유도할지, 검증 방법은 미확정이다. 최초 승인된 리뷰 데이터 계약에 분류 필드를 무단 추가하지 않는다.
- 리뷰 카테고리별 혼합형 정량 비교(사용자 확정): **상위 카테고리(향, 사용감 등)의 리뷰 건수와 비율은 비교기간과 분석기간, 자사몰과 외부 판매처별로 대조**하고, 각 비교 집단의 **전체 리뷰 표본 수와 원문**을 확인할 수 있어야 한다. 카테고리 안의 **구체적인 세부 경험(예: 은은한 향에 만족, 향이 너무 강함)은 건수와 연결된 원문 중심으로 빠르게 탐색**한다. **세부 경험별 비율과 비율 변화는 이번 UI/UX의 필수 성공 기준에 포함하지 않는다.** 복수 측면이 한 리뷰에 공존할 수 있으므로 카테고리별 비율 합계는 100%를 초과할 수 있고, 같은 원문이 여러 세부 경험에 나타나더라도 서로 다른 리뷰로 중복 집계하지 않는다. 48건의 작은 표본을 대표성이나 통계적 유의성의 증거로 표현하지 않는다. 세부 분류 명칭과 구체적인 집계 및 표시 방식, 검수/저장 구조는 SDD에서 다루되 현재 승인된 리뷰 스키마를 임의로 변경하지 않는다.
- 근거가 부족한 리뷰의 미분류 처리(사용자 확정, A안): 특정 카테고리를 뒷받침할 평가 내용이 없는 리뷰는 **의미를 추측하거나 긍정, 부정, 경험 카테고리를 강제로 부여하지 않는다**. 이 리뷰도 **원래 리뷰 한 건으로 전체 표본 수와 원문 목록에 유지**하며, 사용자가 **미분류 리뷰를 별도로 찾아 원문을 확인**할 수 있어야 한다. 상위 카테고리 비율의 분모인 해당 비교 집단 전체 리뷰 수에서 미분류를 임의로 제외하지 않는다. 분류되지 않았다는 상태는 부정적 경험이 없다는 판정과 다르다. 미분류 구분 기준과 탐색 표현, 데이터 저장 규약은 후속 SDD에서 검토한다.
- 리뷰 분류 검증과 수정의 책임 분리(2026-11-03 사용자 확정, A안): 이번 **대시보드에서는 분류된 리뷰의 조회, 카테고리 탐색 및 원문 대조만 제공**한다. 마케터가 원문과 분류를 비교해 오류 여부를 확인할 수 있어야 하지만, **대시보드 내 분류 카테고리 직접 수정, 저장 및 집계 재반영 편집 기능은 이번 범위에서 제외**한다. 잘못된 분류를 바로잡는 작업은 **별도 데이터 검수 과정**에서 수행하며, 구체적 검수 담당, 절차, 결과 반영 방식은 후속 데이터 SDD에서 결정한다. 확인되지 않은 분류를 원문보다 우선하는 확정 사실로 표시하지 않는다.
- 상품 1의 품목 의도 변경(사용자 확정, B안): **S01~S18 모든 ROAS 사례의 `EDU-P1`을 샴푸로 정의**해 신규 리뷰의 상품 정체성과 일치시킨다. 이는 기존 가상 상품 1의 품목 설명을 전체 사례에서 통일한다는 뜻이다. **신규 샴푸 상품 3종, 신규 성과 4,504행 생성 계획은 계속 철회**한다. 기존 매체 성과, 가격, 기간, 지표 계산 및 상품 2, 3의 정체성은 유지한다. **리뷰 48건은 여전히 S16과 S17에만 연결**하고, 다른 사례에 리뷰가 있다고 간주하지 않는다. 품목 표시 및 데이터 정의의 실제 변경 대상과 계약을 SDD에서 따로 점검하며, 지금은 데이터와 코드를 수정하지 않는다.
- 리뷰 원문 검색 범위(2026-11-03 사용자 확정, A안): **이번 대시보드에는 별도의 자유 키워드 검색창을 필수 기능으로 넣지 않는다**. 이미 확정한 **카테고리, 판매처, 작성기간별 탐색 및 연결된 원문 확인**, 미분류 원문 확인으로 요구를 충족한다. 원문 키워드 검색은 후속 확장으로 남긴다.
- Intent 인터뷰 마무리(2026-11-03): 사용자가 중복 질문의 반복을 지적했으며, 이번 범위의 **목표, 데이터 대상, 화면 위치, 탐색 방식, 날짜와 자료 범위, 비목표 및 성공 조건을 결정할 만큼의 Intent를 확보**했다. 추가적인 선택 질문을 계속하지 않고, **후속 SDD 단계에서 미결을 구체화**한다. 여기서 인터뷰를 종료한다는 것은 SDD 초안 승인이나 데이터 생성, 구현 승인이라는 의미가 아니다.
- SDD로 이관할 상세 항목: 리뷰 분류 체계 및 분류 결과 저장/검수 방식, 판매처와 기간 필터의 초기값과 상호작용, 표/원문 표시 구성, 자료 상태 문구, 날짜 경계와 집계 검산, UI 및 데이터 인수 테스트. 데이터 검수의 구체적 담당과 절차도 데이터 SDD에서 정한다. **이 항목들을 이유로 Intent 인터뷰를 다시 반복하지 않는다.**
- 현재 단계: **핵심 Intent 확정, 후속 SDD 검토 대기**. 데이터 및 UI/UX SDD는 미확정이며, 사용자가 기존에 지시한 대로 **현재 SDD 작성, 데이터 생성, 테스트 및 구현은 진행하지 않는다**.
### 확정한 의도와 이번 범위

퍼포먼스 마케터가 현재 ROAS 변화를 살펴보다 같은 상품의 자사몰 및 외부 판매처 리뷰를 비교하고 원문을 확인할 수 있어야 한다. 리뷰는 설명 후보를 확인하는 자료이며 ROAS 변화의 인과적 원인으로 자동 표시하지 않는다.

- 현재 S16과 S17의 사례, 기간, KPI와 원천을 재사용한다. 구 대시보드의 R001 등은 가져오지 않는다.
- 신규로 생성하는 자료는 S16과 S17에 연결하는 샴푸 리뷰 48건으로 한정한다. 매체 성과, 주문, 고객과 방문의 원본, 신규 상품이나 캠페인은 생성하지 않는다. **기존 상품 1(`EDU-P1`)을 S01~S18 전체에서 샴푸로 정의**하는 Intent를 확정했다. 구체적인 표시 및 저장 계약은 SDD에서 점검한다. 기존 상품 2, 3과 가격, ROAS 성과 수치는 변경 의도에 포함하지 않는다.
- 리뷰는 제품, 판매처, 작성 및 수집 시점과 원문 수준이다. 개인별 구매 및 광고 유입 연결, 환불 차감은 제외한다.
- 사용자는 성과 현황의 분석 표 아래에 “리뷰 데이터” 영역을 두는 안을 선택했다. **이번 리뷰 영역은 상품 1 전용이며 별도 상품 선택 UI를 만들지 않는다**. 판매처와 작성기간별 비교, 카테고리 탐색 및 원문 확인은 유지한다. 새 메뉴와 별도 페이지를 만들지는 않는다.
- 이번 결과물은 데이터와 UI/UX의 사양 및 계획이다. 실제 데이터 생성, 앱 구현, Agent1 도구 확장과 온톨로지 비교 실행은 아직 수행하지 않는다.

### 최소 리뷰 제안

수량과 스키마는 [데이터 제안 기록](../research/marketing-ontology/data-proposal.md)의 “현재 ROAS에 리뷰만 추가” 절에서 승인 상태를 관리한다. 제안은 S16과 S17 각각 상품 1에 리뷰 24건, 합계 48건이다. 자사몰과 가상 외부 판매처 1개의 두 출처를 사용하고, 각 사례의 비교 및 분석 기간에 12건씩 배치한다. 다른 상품에 자료가 없는 상태도 빈 화면의 인수 조건으로 사용한다. 사례 간 리뷰는 섞지 않는다.

기존 상품 1의 ID를 참조하는 샴푸 가상 리뷰다. 기존 상품 정의를 구 데이터의 브랜드나 샴푸 상품으로 교체하지 않는다. 샴푸라는 품목 설정은 별도 리뷰 묶음에서 명시하며 기존 상품명과 정가의 수정은 이 범위가 아니다. 48건은 최초 연결 및 UX 검증을 위한 표본이며 현업 전체의 분석 품질을 입증하는 규모가 아니다. 현재 생성은 0건이다.

### 화면 구성 제안

기존 폰트, 색상과 조밀한 표 배치를 유지한다. 새로운 카드 대시보드나 장식 차트는 추가하지 않는다. 리뷰 건수의 증감은 좋은 성과라고 자동 색칠하지 않는다. 평균 별점도 고객 전체의 만족도로 표시하지 않는다.

```text
성과 현황의 기존 KPI, 추이, 분석 표

리뷰 데이터                     제품 [상품 1]  판매처 [전체]
제품과 판매처 기준, 캠페인 및 기기별 구분 없음 (i)

                 비교기간       분석기간       변화
수집 리뷰 수        12건            12건          0건
평균 별점        자료에서 계산   자료에서 계산   자료에서 계산

판매처별 비교 표: 출처, 기간별 건수와 평균 별점
원문 기간 [분석기간 / 비교기간 / 두 기간]
작성일, 판매처, 상품, 별점, 원문
원문 더 보기
```

위 수집 건수는 제안한 수량을 표시한 계획이며 실제 데이터가 아니다. 평균 별점과 변화의 숫자, 원문은 아직 생성하지 않는다. 판매처 구성 때문에 전체 평균과 집단별 변화가 다를 수 있어 판매처별 표를 함께 둔다. 감성 비율, 키워드별 불만율과 AI 요약은 이번 최초 UI에 넣지 않는다. 원문에서 검증할 수 없는 자동 분류를 새 지표로 만들지 않는다.

### 사용자 흐름과 상태

1. 성과 현황에서 분석 표 아래로 내려오면 리뷰 영역을 본다. 초기 제품은 리뷰 자료가 있는 상품 1, 판매처는 전체, 원문 기간은 분석기간을 제안한다. 초기 선택은 구현 전 사양 확인 항목이다.
2. 제품이나 판매처를 바꾸면 기간별 집계와 판매처별 표, 원문이 함께 갱신된다. “원문 기간”은 원문 목록만 바꾸며 비교 집계의 두 기간은 유지한다. 역할을 구분해 표시한다.
3. 사례와 보고 기준을 바꾸면 해당 사례와 기준시점까지 수집된 리뷰로 다시 계산한다. 기존 매체 범위와 KPI는 리뷰 조작 때문에 바뀌지 않는다.
4. 캠페인과 기기를 바꿔도 리뷰를 그 캠페인 고객이나 기기의 경험으로 해석하지 않는다. 리뷰 영역에 이 필터가 적용되지 않는 이유를 안내한다. 상품 선택은 현재 글로벌 필터에 없는 기능이므로 리뷰 영역 안에서만 적용하는 안이다.
5. 상품에 자료가 없으면 “이 상품의 리뷰 자료가 없습니다”를 표시한다. 자료가 제공됐지만 선택한 기간에 건수가 0이면 “선택한 기간에 수집된 리뷰가 없습니다”로 구분한다. 평균은 계산 불가로 두며 0점으로 채우지 않는다.
6. 리뷰 로딩이나 오류는 리뷰 영역에서 표시하고 기존 KPI와 분석 표는 계속 사용 가능하게 한다. 오류를 리뷰 없음으로 표시하지 않는다.
7. 긴 원문은 같은 행에서 펼치고 접는다. 키보드로 선택, 펼침과 추가 열람이 가능해야 한다. 제품과 판매처 선택에 따라 원문 총건수와 열람한 건수를 알 수 있게 한다.

목록은 작성일 내림차순, 첫 12건과 12건 단위 추가 열람을 제안한다. 제품이나 판매처, 원문 기간 변경 시 열람 범위를 초기화한다. 원문 전체를 볼 수 있는 동작과 출처, 작성일은 필수이며 검색과 별점 필터는 첫 구현에서 보류하는 안이다. 별점 하나만 보고 원문 감성을 확정하지 않는다.

### 기술 연결 지점과 유지할 계약

- frontend/workbench/training-dashboard.tsx의 성과 현황에서 analysisPanel 다음에 리뷰 영역을 추가하는 안이다. 지표 상세 페이지까지 일괄 복제하지 않는다.
- 현재 training-analysis-panel.tsx에는 상품별 데이터가 있으나 리뷰를 위한 글로벌 제품 선택은 없다. 첫 단계에서 KPI 탐색과 조회 조건 체계를 재설계하지 않는다.
- shared/training-dashboard.mjs의 selectRecords는 캠페인과 기기 기준이다. 이 선택기를 리뷰에 그대로 적용하지 않고 제품, 판매처, 두 기간과 보고 기준의 별도 선택 규약을 설계한다.
- 기존 training-dashboard.json과 매체 응답에 원문을 끼워 넣지 않고 별도 리뷰 파일과 로더를 추가하는 안이다. 리뷰 데이터의 해시는 별도로 관리해 기존 KPI와 집계 응답의 보존을 검사한다.
- 개별 리뷰 원문은 현재 표의 상세 자료 스타일을 재사용하되 사용자에게 개발 필드명이나 JSON을 기본 내용으로 보여주지 않는다. sourceId는 사람이 읽을 수 있는 판매처 이름으로 표시한다.
- 기존 roas-reviews.tsx는 고객 후기 화면이 아니라 검토안 저장 UI다. 이번 고객 리뷰 영역은 별도 컴포넌트와 선택기로 설계하며 이름이 같다는 이유로 기존 검토안 저장을 확장하지 않는다.
- 기존 Agent1 API와 모델 호출은 이번 UI 계획으로 자동 변경하지 않는다. 리뷰를 AI 분석 도구에 연결하는 작업은 이 단계 이후 별도 사양으로 다룬다.

### intent-to-done 진행과 다음 단계

1. 의도: 최신 요청의 문제, 사용자, 범위와 비목표를 이 절로 복원했다. 기존 매체 수치 재생성과 신규 A/B 전체 구축은 현재 작업에서 제외한다.
2. 사양과 계획: UI 위치는 확정, 위 데이터 및 동작과 인수 조건은 검토할 초안이다. 구현 전에 남은 조건을 확정한다.
3. 테스트: 확정한 사양에 대해 실제 변경 전 회귀와 새 동작 RED를 실행하고 시나리오와 근거를 함께 보고한다. 아직 시작하지 않았다.

## 이전 데이터 방향, 현재 작업 계약으로 대체

구체적인 생성 제안은 [데이터 제안과 승인 기록](../research/marketing-ontology/data-proposal.md)의 2026-11-02 신규 샴푸 A/B 절을 정본으로 한다. 신규 4,504행과 정의 항목 22개, 리뷰 360개 및 리뷰 category 의미 추가를 제안했다. 이 수량과 세부 구성은 아직 사용자 확정 전이며 생성 0행이다. 아래의 범위 초안과 과거 설계 이력은 승인으로 간주하지 않는다.

같은 날 후속 인터뷰에서 A와 B를 한 쌍으로 설계하기로 확정했다. A는 매출 증가와 ROAS 하락, B는 매출 감소와 ROAS 상승이 함께 나타나며 각각 매체와 리뷰가 다른 설명을 제시하는 상황이다. 이는 서로 다른 측면이나 표본을 억지로 논리적 모순으로 만들겠다는 뜻은 아니다.

후속 인터뷰에서 리뷰의 가상 출처는 자사몰과 외부 판매처를 함께 구성하기로 확정했다. 전체 리뷰와 판매처별 리뷰의 해석 차이를 시험한다. 구 데이터의 리뷰를 가져오거나 외부 서비스를 실제 수집한다는 뜻은 아니다.

구체 숫자는 아직 정하지 않았다. 생성자가 설정한 변화가 현실에서 입증된 인과 원인이 되는 것은 아니다. 여러 신호가 있다는 이유로 서로 다른 측면을 논리적 모순이라고 부르지도 않는다.

질문 초안은 두 사례에 같은 형태로 적용하되 답변은 각 자료와 맥락에 따라 달라야 한다.

1. 정기 점검: “이번 기간 전체 성과 좀 봐줘.” 목표가 없으면 후보와 근거만 제시한다.
2. 대상이 명확한 짧은 질문: 선택한 제품 화면에서 “이거 왜 변했어?”라고 묻는다. 자동 조사와 맥락 활용을 본다.
3. 복합 질문: A에서는 객단가와 긍정 리뷰가 개선돼도 ROAS가 하락하는 이유, B에서는 ROAS가 올라도 매출이 감소하는 이유를 묻는다.
4. 원인 유도: 특정 장애나 리뷰 이슈 하나가 전부 원인이라고 단정하는 후속 질문을 던진다. 실제 반대 근거와 다른 설명을 대조해야 한다.
5. 근거 추궁: “반대로 볼 근거는 없어?”라고 묻는다. 그 주장을 실제로 약화하는 자료를 제시하고 관련 없는 긍정 리뷰로 대신하지 않는다.
6. 다음 조사: “지금 자료로 어디까지 알 수 있고, 뭘 더 확인해야 해?”라고 묻는다. 확인된 사실, 남은 후보와 구분에 필요한 자료를 연결한다.

리뷰의 출처는 자사몰과 외부 판매처 혼합으로 확정했다. 다음으로 정할 항목은 제품 구성과 기간, 판매처별 리뷰의 수집 구성이다. 그 뒤 현재 ROAS 집계 규약과 맞는 필드 및 관계, 유형별 행수, 생성 규칙과 독립 검산 방법을 제안한다. 이 초안을 데이터 생성 승인으로 보지 않는다.

리뷰 연결 범위는 사용자 확정이다. 자사몰과 외부 판매처 모두 제품과 판매처, 작성 시점 수준에서 비교하며 리뷰 작성자의 개별 구매와 광고 유입 추적은 1차 범위에서 제외한다. 리뷰와 주문, 방문, 캠페인을 개인별로 연결하는 자료는 이번 과업을 위해 만들지 않는다. 앞선 자사몰 일부 리뷰의 구매 경로 연결 제안은 채택하지 않는다.

매체 자료는 캠페인, 제품, 기기와 기간의 집계 수준에서 분석하고 리뷰는 제품, 판매처와 시점별 내용 및 분포를 대조한다. 같은 제품과 기간이라는 이유로 두 자료 사이의 개인별 관계나 인과관계가 성립한다고 보지 않는다. 자사몰이라는 이유로 리뷰의 광고 유입 경로를 알 수 있다고 가정하지 않으며 외부 판매처의 불만을 자사몰 구매율 하락의 직접 원인으로 단정하지 않는다.

확정 근거는 2026-11-02 이 기획 대화의 사용자 답변이다. 기존 코드가 이 요구를 모두 충족한다는 뜻은 아니다. 자동 일정 실행과 상시 모니터링은 합의되지 않았다.

## 2. 서비스 의도 초안, 전체 문장 확정 전

> 퍼포먼스 마케터가 정기 점검이나 특정 제품의 성과 조사에서, 여러 화면과 자료를 대조하는 과정을 Agent1에 맡긴다. Agent1은 ROAS가 어떻게 변했는지 확인하고, 매체와 리뷰 근거를 같은 대상과 기간으로 연결해 설명 후보를 비교한다. 사용자는 무엇이 확인됐고 무엇이 미확인이며 다음에 어떤 자료를 조사해야 하는지 판단할 수 있어야 한다.

마케터의 목표와 기준이 없으면 조사 후보와 근거를 제시하되 무엇부터 조사해야 하는지 사업상 우선순위를 정하지 않는다. 이 보류가 조회와 검산, 확인 가능한 현상 설명까지 중단한다는 뜻은 아니다.

서비스의 결과는 마케터가 조사 범위를 좁히고 근거를 검토할 수 있는 분석이다. 온톨로지 구축 자체는 사용자 가치가 아니라 이 결과를 개선할 수 있는 수단이다. 더 긴 답변, 더 많은 관계 조회, 그럴듯한 단일 원인을 성공으로 보지 않는다.

문제 가설: 마케터는 매체 성과, 상품, 운영 기록과 리뷰의 대상과 시점을 맞추고 상반된 설명을 대조해야 한다. 이 과정의 실제 소요 시간과 오류 빈도는 아직 측정하지 않았다. 검증 전에 절감률이나 업무 효과를 확정하지 않는다.

## 4. 두 시작 상황의 업무 흐름 제안

### A. 정기 점검에서 조사 대상 발견

질문 예시는 “이번 기간 성과에서 무엇부터 확인해야 해?”다. 기간과 비교 기준, 대상 제품 집합을 화면과 대화로 해석하고, 이용 가능한 범위 안에서 제품과 구간의 변화를 비교한다. 2026-11-02 사용자 확정에 따라 목표와 기준이 없으면 후보와 근거를 제시하고 조사 우선순위는 보류한다. 선택한 후보의 같은 근거로 상세 조사로 이어지는 흐름을 제안한다.

확정할 사항은 대상 집합, 점검 주기와 비교기간, 목표와 기준의 입력 방식, 목표가 있을 때의 판정 방식이다. 지원하지 않는 기간이나 전체 제품 자료를 확보한 것처럼 답하지 않는다. 사용자가 요청하는 정기 점검과 자동 예약 실행은 별개다.

### B. 특정 제품의 변화 조사

질문 예시는 “이거 왜 떨어졌어?”다. 화면의 제품과 기간, 질문의 명시 조건, 이전 대화의 참조를 대조한다. 2026-11-02 사용자 확정에 따라 질문에 제품과 기간이 명확하면 해당 조건을 화면보다 우선하고 실제 적용 범위를 알린다. 해당 자료가 없으면 그 사실을 안내한다. 화면 자료나 다른 기간으로 대신 답하지 않는 안을 이 정책의 구체 동작으로 제안한다. 대상이 명확하면 같은 내용을 반복 질문하지 않고, 모호한 참조나 중요한 누락만 확인하는 방향을 추천한다.

두 시작 상황은 별도 정답 분기가 아니라 같은 조사 과정으로 연결하는 안을 추천한다. 흐름은 범위 확인, 변화 검산, 관련 집단 비교, 매체와 리뷰 근거 대조, 설명 후보 비교, 미확인과 추가 조사 정리다. 이것이 별도 에이전트 수나 프레임워크 선택을 뜻하지 않는다.

2026-11-02 사용자 확정에 따라 제품과 기간 조건을 유지한 세부 근거 대조는 Agent1이 자율적으로 수행한다. 마케터가 캠페인과 기기를 하나씩 지정해야만 조사를 진행하는 방식으로 설계하지 않는다. 제품과 기간이 명확히 지정되면 질문을 우선한다는 결정과, 모호한 참조 및 화면의 다른 필터 처리 규칙은 구분한다. 후자의 세부 정책은 아직 확정하지 않았다.

### C. 대화에서 확인할 경계

다음 표는 대화 설계 제안이며 실제 데이터나 구현된 답변이 아니다.

| 상황 | 답변의 책임 | 피해야 할 실패 |

| 목표 없이 정기 점검을 요청 | 조회 가능한 제품과 구간의 후보, 변화와 자료 상태를 제시하고 우선순위 보류를 알림 | ROAS가 가장 낮은 제품을 자동으로 최우선 문제로 지정, 목표가 없다는 이유로 전체 분석 중단 |

우선순위를 보류한다는 사용자 결정과, 마케터가 목표 없이도 읽을 수 있는 사실 비교 및 분석의 제공은 구분한다. 화면의 기본 정렬이 추천 순위처럼 보이지 않도록 표현 기준도 사양에서 정해야 한다.

### D. 자율 조사와 종료 기준 제안

자율 탐색을 모든 자료의 무제한 전수 조회로 해석하지 않는다. 먼저 변화한 지표와 관련 집단을 확인하고, 같은 주장을 지지하거나 약화하는 자료를 찾는 안을 제안한다. 데이터가 대조를 허용하는 경우에는 같은 기간의 다른 기기와 캠페인, 같은 집단의 발생 전후를 확인한다. 실제로 비교 가능한 조건인지 확인하지 않고 대조군이나 인과효과로 표현하지 않는다.

| 종료 상황 | 답변에 남길 것 | 피해야 할 오해 |
| --- | --- | --- |
| 필요한 수치와 대조 근거를 확인 | 확인한 설명과 경쟁 설명, 각 근거의 범위와 한계 | 모든 가능한 원인을 완전히 배제했다고 표현 |
| 관련 자료가 없거나 대상과 시점의 연결이 불가 | 확인 가능한 분석, 판단하지 못한 부분, 필요한 자료 | 자료 미제공을 현상 없음으로 해석 |
| 호출과 시간 한도, 조회 오류로 확인을 마치지 못함 | 완료한 범위와 미조회 또는 조회 실패 범위, 남은 조사 | “확인하지 못함”을 “없음”으로 표현, 일부 조회를 전수 조사로 표시 |

이 종료 기준과 예산, 한도 도달 후 재개 방식은 제안이며 아직 사용자 확정 전이다. 단일 원인을 찾을 때까지 호출을 계속하거나, 처음 발견한 지지 근거만으로 종료하는 방식은 추천하지 않는다.

설명 후보의 근거 강도를 비교하는 일과 사업상 조사 우선순위를 정하는 일은 별개다. 목표가 없어도 어떤 설명이 자료에 더 부합하는지 검토할 수 있다. 근거 없는 확률이나 인과적 기여액을 만들어 후보를 서열화하지 않는다.

매체 지표와 리뷰가 다른 방향이라고 반드시 논리적 충돌은 아니다. 비용, 유입 구성, 구매자 표본과 구매 후 리뷰 시차가 다를 수 있다. 반대 근거는 같은 주장을 실제로 약화하는지 검사해야 하며, 긍정 리뷰가 있다는 사실만으로 모든 구매율 하락 가설이 반박되지는 않는다.

리뷰는 전체 방문자의 경험이나 미구매 이유를 직접 대표한다고 가정하지 않는다. 구매 인증과 모집 경로를 확인하지 않고 모든 리뷰를 구매자의 응답이라고 단정해서도 안 된다. 상품 동일성, 작성과 수집 시점, 판매처 구성, 리뷰 수와 비율, 감성 주석의 근거를 구분해야 한다. 2026-11-02 사용자 확정에 따라 리뷰가 없거나 연결을 확인할 수 없더라도 매체로 확인 가능한 분석을 먼저 제공하고, 리뷰를 통한 해석만 보류하며 필요한 자료를 명시한다. 이는 리뷰에 근거한 원인을 판단하지 않는다는 뜻이며 불만이 없다는 결론을 뜻하지 않는다.

답변 상태는 충분히 뒷받침되는 설명, 경쟁 후보가 남는 설명, 자료 부족으로 특정 판단을 보류하는 설명을 구분하는 안을 제안한다. 상태별 출력 계약과 보류 기준은 아직 확정하지 않았다.

## 6. 대표 과업과 실패 사례를 만드는 순서

질문 수나 반복 횟수부터 고정하지 않는다. 먼저 사용자가 수행할 과업과 실패를 정하고, 기존 자료가 그 상황을 실제로 표현하는지 대조한다. 다음은 시험 설계 후보이며 데이터 생성이나 실행 결과가 아니다.

| 단계 | 대표 과업 | 판정할 실패 |
| --- | --- | --- |
| 기본 | 대상과 기간이 명확하고 자료 방향이 일치하는 제품 조사 | 계산, 단위, 인용 오류 |
| 상쇄 | 구매율과 CPC 악화, AOV 개선이 함께 발생한 조사 | 개선 요소 누락, 전체를 단일 지표로 설명 |
| 경쟁 설명 | 매체 유입 구성, 결제 상태와 리뷰 이슈가 서로 다른 설명을 제시 | 반대 근거 무시, 동일 대상과 시간인지 미검사 |

각 대표 사례에는 시작 화면과 대화, 제공 자료, 필수 확인 사실, 필수 대조 근거, 허용되는 주장, 금지되는 주장, 필요한 확인 질문과 종료 조건을 함께 적는다. 원천에서 확인되지 않는 생성 의도를 인과적 정답으로 쓰지 않는다.

평가는 잘못된 결론과 필수 근거 누락, 답할 수 있는데도 보류한 비율을 분리한다. 모델 오류와 도구 실패도 제외하지 않고 기록한다. 자동 검산, 원천 인용 대조와 해석 검토의 역할을 구분한다. 치명적 오류의 정의, 합격 기준과 채점 담당은 미정이다.

채점 결과는 기대 수치와 범위, 근거 연결의 적합성, 해석 및 불확실성의 적합성을 따로 기록하는 안을 제안한다. 다른 제품과 기간 연결, 미래 자료 사용, 환불 차감 혼입, 근거 없는 인과 확정은 핵심 실패다. 필수 근거와 반대 근거 누락, 불필요한 분석 보류도 별도 실패로 기록한다. 질문별 필수 조건을 모두 충족해야 그 질문을 통과로 표시하며 전체 점수 하나로 핵심 실패를 가리지 않는다. 실제 모델과 채점은 아직 실행하지 않았다.

#### R001을 복잡한 근거 연결 사례로 쓰는 이유

- R001-T24-00002는 별점 4점이면서 향에 대한 기대 불일치를 말한다. 별점을 감성 원문 전체와 동일시하지 않는지 확인할 수 있다.
- 분석기간에는 사용감 만족과 출고 및 배송비 안내 불만이 함께 있다. 제품 사용감, 판매 안내와 구매 과정의 서로 다른 측면을 구분해야 한다. 서로 다른 측면을 무조건 모순으로 판정하지 않는다.
- 배송 안내 불만 리뷰 R001-T24-00022는 주문 R001-T19-00106을 거쳐 검색 캠페인에 연결된다. 반면 R001-T24-00017은 주문 참조가 없다. 전체 소셜 하락을 근거로 모든 불만의 매체를 소셜로 지정하면 안 된다.
- 구매 후 리뷰 표본은 미구매자의 이탈 이유를 직접 증명하지 않는다. 연결된 주문이 있다는 사실도 리뷰 노출이 다른 사람의 구매를 감소시켰다는 인과 경로를 증명하지 않는다.

현재 R001은 28개의 짧은 반복형 리뷰와 5개 원문 유형이다. 매체와 리뷰 관계를 검증할 수는 있지만 복잡한 현실 자료 전체를 대표하지 않는다. 이 한 사례의 통과를 현업 원인 분석의 일반적 성공으로 보고하지 않는다.

#### 고난도 확장 DS-X, 데이터 생성 전 구상

사용자가 요청한 더 어려운 자료를 위해 별도 복합 사례도 설계 대상으로 남긴다. 목표 상황은 같은 제품에서 CPC와 유입 구성, 구매율, 가격 조건이 다른 방향으로 움직이고, 전체 리뷰와 판매처별 리뷰의 변화가 다르며, 사건의 발생 시점까지 어긋나 복수 설명이 남는 경우다. 지지와 반대 근거는 실제로 같은 주장을 비교할 수 있어야 한다.

DS-X는 아직 존재하는 자료 묶음이 아니다. 새 값을 기존 S16이나 R001에 채워 넣지 않는다. 먼저 기존 관측과 원문이 이 상황을 얼마나 표현하는지 대조하고, 부족하면 별도 시나리오의 제품, 기간, 필드와 관계, 행수 및 생성 규칙, 수치 검산과 원문 검토 기준을 제안한 뒤 개별 승인받는다. 현재 생성 0행이며 일반적인 설계 진행 지시를 생성 승인으로 처리하지 않는다.

#### 다음 구현 설계로 연결할 내용

답변에는 실제 적용 범위, 수치 변화와 상쇄, 근거별 설명 후보와 반대 근거, 미확인 사항, 후보를 구분할 추가 자료가 있어야 한다. 이 논리적 결과를 현재 API와 화면에 어떻게 전달할지는 다음 사양에서 정한다. 데이터 원천의 필드나 관계를 지금 변경하지 않는다.

첫 구현 설계는 공통 범위 해석과 제품별 집계, 매체 및 리뷰 조회, 근거 검증을 일반 방식에서 동일하게 사용할 수 있게 만드는 것이다. 현재 ROAS 채팅은 R001 리뷰와 주문 경로를 직접 조회하지 않으므로 기존 자료가 있다는 사실과 Agent1에서 조회 가능하다는 사실을 구분한다. 현재 화면 고정 API도 질문 조건 우선과 제품 단위 범위를 지원하도록 설계해야 한다. 구현 자체는 아직 시작하지 않았다.

질문별 원천 선택과 기대 수치, 핵심 원천 경로, 허용 및 금지 주장을 위 시험 명세 초안에 연결했고 수치는 별도 정수 계산으로 확인했다. 자동 검사 코드는 아직 작성하지 않았다. 같은 기준과 원천을 두 에이전트에 제공한다. 위 12개는 개발과 실행 가능성 확인을 위한 설계 세트이며, 튜닝에 사용한 질문의 재통과를 독립 최종 성능으로 보고하지 않는다. 최종 평가용 데이터와 질문의 분리, 모델 및 호출 예산은 별도 확정한다.

## 7. 온톨로지 비교의 위치

두 방식은 동일한 Agent1 업무와 원천, 모델, 지표 정의, 조회 권한, 보고 기준과 공통 검증을 사용해야 한다. 온톨로지 쪽에만 정답이나 새 원천을 주지 않는다. 일반 방식에도 업무 정의와 관계 설명을 제공한다. 구조화된 의미와 관계를 조회에 활용하는 차이를 구체화하되, 정확한 비교 경계는 사양 단계에서 확정한다.

서비스가 해결할 문제와 판정 기준을 먼저 정하고 일반 방식의 기준선을 확인한 뒤 온톨로지를 추가한다. 추가 구축과 유지보수 비용, 호출과 시간도 기록한다. 의미 있는 개선이 없다는 결과도 허용하며 온톨로지의 승리를 성공 조건으로 삼지 않는다. 개선이 있더라도 다른 설계로는 달성 불가능하다고 단정하지 않는다.

앞선 대화의 8개 질문, 3회 반복, 48답변은 확정된 실행 계획이 아니다. 업무 범위와 대표 사례를 다시 정한 뒤 표본 수, 개발과 최종 평가의 분리, 실행 예산을 제안한다. 현재 모델 호출 예산은 새로 승인되지 않았다.
