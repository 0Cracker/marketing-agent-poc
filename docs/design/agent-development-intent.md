# 에이전트 개발 Intent

갱신: 2026-11-04, Asia/Seoul.
상태: 에이전트 개발 의도 확정, **SDD-01~60 사용자 정책 확정(비-Gemini 생성 모델 자동 대체 허용, 한도 소진 시 즉시 전환)**. SDD-54 A는 인증 게이트웨이와 PC 아웃바운드 터널, SDD-55 A는 단일 Node 서버 비동기 Run Engine, **SDD-56은 공용 QA 테스트 계정 하나**, **SDD-57 A는 실행 중 검증된 메모리 원천 스냅샷**. 사용자별 계정/영속 스냅샷 저장소는 이번 PoC 범위에서 제외. Agent Architecture, Workflow, 7개 Tool 구현 계약과 QA 참여자의 인증된 외부 접근 경계는 에이전트 개발 SDD §27~34에서 관리한다. §33~34는 Gemini 직접 무료 티어와 Vercel AI Gateway 제공 크레딧, Sail Research의 별도 무료 크레딧을 구분하면서 적격 비-Gemini 모델도 한도 소진 시 즉시 자동 대체하도록 확정한다. 실제 코드 구현, 테스트, 실 API 호출, 발행은 미착수. 모델 선택/운영비 정책은 SDD §13과 최신 §33에 따른다.

이 문서는 에이전트 개발, 공통 조사 flow와 데이터 접근 환경, 온톨로지 비교의 의도 정본이다. 사용자의 문서 분리 요청에 따라 기존 리뷰 Intent에 추가했던 에이전트 개발 내용을 이 파일로 이관했다. 의도 변경은 이 파일에서, 상세 동작 계약과 사양 인터뷰는 [에이전트 개발 SDD](agent-development-sdd.md)에서 관리한다.

## 1. 해결할 문제와 원하는 결과

퍼포먼스 마케터가 기존 대시보드 채팅에서 정기 성과 점검과 특정 상품의 ROAS 변화를 질문하면, 에이전트가 제공된 데이터 도구로 전체 상황과 자료 상태를 확인하고 핵심 설명 후보와 반대 근거를 자율적으로 대조한다. 확인한 사실, 설명 후보와 한계, 추가로 확인할 자료를 답해 마케터의 실무 분석을 지원한다.

온톨로지 구축은 이 결과를 개선할 수 있는 수단이다. 일반 방식과 동일한 기본 도구에 온톨로지 도구를 추가해 잘못된 결론의 감소와 추가 구축의 가치를 비교한다. 온톨로지 방식의 우위를 성공 조건으로 삼지 않는다.

## 2. 이번 인터뷰에서 사용자와 확정한 결정

| 항목 | 확정한 방향 |
| --- | --- |
| 첫 개발 단위 | no ontology 에이전트를 기존 대시보드 채팅에 연결해 화면 조건과 대화를 받고, 실제 데이터를 조사해 답변하는 것까지 |
| 조사 방식 | 전체 개요를 먼저 확인하고 핵심 설명 후보와 반대 근거를 따라 추가 조사 |
| 조사 자율성 | 필요한 조사 순서와 도구 선택을 에이전트에게 맡김. 처음 발견한 지지 근거만으로 끝내지 않고 반대 근거가 나오면 조사 방향을 바꾸거나 추가 확인 |
| 기본 도구 환경 | 제공된 데이터의 조회와 분석 도구를 충분히 제공. 에이전트용 샌드박스에서 임의 코드를 실행하는 환경은 제외 |
| 비교 구성 | no ontology는 기본 데이터 도구, ontology는 동일한 기본 데이터 도구 + 온톨로지 도구. 두 방식 모두 기본 도구로 원천 근거 확인 가능 |
| 답변 전 검토 | 우선 조사 에이전트 하나 + 수치, 대상, 기간, 인용의 자동 검사 |
| 해석 품질 평가 | 별도 QA에서 평가하고, 매 답변을 검토하는 추가 에이전트의 도입 여부는 QA 결과로 판단 |
| 응답 시간 | 단순 질문은 몇 초 이내 목표. 복잡한 조사나 정확도가 중요한 내용은 몇 분 대기 허용 |

응답 시간은 목표의 방향이며 실측 결과나 성능 보장이 아니다. 단순 질문의 정의와 구체적인 초 단위 목표, 최대 실행 시간은 SDD에서 정한다. 자동 검사만으로 해석의 타당성이 검증됐다고 간주하지 않는다.

사용자는 병행 작업에서 에이전트 대시보드 UI를 건드리지 않는다고 설명했다. 병행 중이라는 이유로 대화 연결을 후속으로 미루지 않는다. 답변 포맷의 본격적인 정형화와 UX 고도화는 후속 발전 단계로 유지한다.

## 3. 유지할 기존 업무 경계

아래는 이전 인터뷰에서 확정한 업무 경계를 이어받은 것이며, 이번 분리로 새로 결정한 정책이 아니다.

- 첫 사용자는 퍼포먼스 마케터이며 서비스 목적은 실무 분석 지원이다.
- 정기 성과 점검에서 조사 대상을 찾는 상황과 특정 상품의 ROAS 변화를 조사하는 상황을 모두 지원한다.
- 현재 대시보드의 ROAS 정의를 사용하며 환불 차감은 이번 분석과 평가에서 고려하지 않는다.
- 질문에 상품과 기간이 명확하면 화면보다 질문 조건을 우선하고 적용한 범위를 알린다. 자료가 없으면 그 사실을 안내한다.
- 마케터의 목표와 기준이 없으면 후보와 근거를 제시하되 사업상 조사 우선순위는 보류한다. 확인 가능한 수치 분석까지 중단하지 않는다.
- 분석 결과는 원인 후보, 확인할 근거와 추가 조사까지다. 유지와 중단 같은 조치 추천이나 광고 변경은 이번 범위에 포함하지 않는다.
- 같은 상품과 기간의 리뷰가 없거나 연결이 불확실해도 매체로 확인 가능한 분석을 먼저 제공하고 리뷰를 통한 해석만 보류한다.
- 리뷰는 상품, 판매처와 시점 수준에서 비교한다. 개별 고객의 구매와 광고 유입을 근거 없이 연결하거나, 리뷰와 ROAS의 인과관계를 단정하지 않는다.

## 4. 공통 flow의 논의용 초안

질문과 범위 확인 → 전체 개요와 자료 상태 확인 → 조사 계획 → 도구 조회와 계산 → 핵심 설명 후보와 반대 근거 대조 → 부족하면 추가 조사 → 자동 검사 → 근거와 한계를 포함한 답변.

위 순서는 확정한 조사 방식을 구체화하기 위한 초안이다. 각 단계의 입력과 상태, 조사 종료 판정, 자동 검사 실패 시 재조사와 종료 방식은 아직 확정하지 않았다. 과거 두 역할 B 흐름을 이번 에이전트의 확정 구조로 자동 승계하지 않는다.

조회, 필터, 집계, 지표 계산, 집단 비교와 원문 확인을 재사용 가능한 기본 도구로 제공하는 안을 제안했다. 구체적인 도구 목록과 입력, 반환값, 허용 범위는 SDD에서 정한다. 웹 검색이나 외부 API 사용은 현재 확정 범위에 포함하지 않는다.

## 5. 발전 순서와 비교 원칙

1. no ontology 에이전트와 기본 도구 환경, 기존 대시보드 채팅 연결.
2. 온톨로지 구축과 추가 도구 연결, 일반 방식과 비교.
3. 에이전트 답변 포맷 정형화와 UX 고도화.
4. 에이전트 답변 QA.

이 순서는 사용자 요청의 발전 단계다. 기능 개발 과정의 TDD와 독립 검증, 기본적인 답변 검사를 마지막까지 생략한다는 뜻은 아니다. 비교와 근거 추적에 필요한 최소 답변 계약을 먼저 설계하는 안은 제안 상태다.

비교는 같은 업무와 원천에 온톨로지를 더했을 때의 가치를 확인한다. 일반 방식에도 필드 의미와 지표 정의, 업무와 관계 설명을 제공한다. 온톨로지 방식에만 정답이나 새 원천을 주지 않는다.

모델, 질문, 원천 스냅샷, 공통 지표 정의, 실행 예산과 평가 기준을 맞추는 안을 제안했다. 구체적인 통제 계약, 모델과 호출 예산은 미확정이다. 추가 구축과 유지보수 비용, 호출과 시간을 함께 기록하는 기존 원칙을 유지한다.

## 6. 다른 병행 작업과의 경계

| 작업 | 별도 정본 | 에이전트 작업에서의 취급 |

| 리뷰 원천과 분류, 읽기 전용 데이터 계약 | [리뷰 데이터 SDD](agent1-review-data-sdd.md) | 데이터 담당 작업의 계약을 소비하며, 이 문서에서 생성과 스키마 변경을 승인하지 않음 |
| 리뷰 영역의 화면 배치와 탐색 | [리뷰 UI/UX SDD](agent1-review-ui-sdd.md) | 기존 리뷰 화면의 결정과 책임을 보존 |

사용자는 리뷰 데이터와 UI/UX를 병행 진행 중이며 확정 데이터는 크게 바뀌지 않을 것으로 예상한다고 설명했다. 이 설명만으로 해당 작업의 구현이나 검증 완료를 기록하지 않는다. 리뷰 생성 규칙과 분류 체계, 화면 설계의 상세 내용을 에이전트 문서에 중복 관리하지 않는다.

## 7. 첫 개발 단위의 성공 판단과 상세 미결

첫 완료 범위는 실제 대시보드 대화에서 데이터 조회와 분석 답변이 연결되는 것이다. 원천과 질문 범위, 근거와 수치의 일치, 반대 근거 대조를 확인한다. 자료 공백을 임의로 채우거나 인과관계를 단정하지 않는지도 검증한다. 온톨로지 구축 완료는 첫 no ontology 개발 단위의 완료 조건이 아니다.

아래는 최초 Intent 단계에서 SDD로 이관했던 항목의 기록이다. 현재는 [에이전트 개발 SDD §24~25](agent-development-sdd.md)와 [구현 지시서](agent-development-implementation-handoff.md)에 구현 계약과 남은 기술 검증을 구분해 정리했다.

- 단순 질문과 심층 조사의 구분, 구체적인 응답 시간 목표와 실행 한도.
- 공통 flow와 시스템 아키텍처, 실행 상태와 대화 맥락, 모호한 범위의 추가 질문.
- 기본 도구와 온톨로지 도구의 계약, 데이터와 보고 기준의 일치.
- 조사 종료 판정, 자동 검사 규칙, 도구 오류와 검사 실패 시 동작.
- 최소 답변 계약, 실행 기록, QA의 합격 기준과 비교 조건.
- 모델과 프레임워크, 호출 한도와 비용.

이 문단과 위 항목은 Intent 작성 당시의 미결 기록이다. SDD-01~35의 사용자 확정 정책과 구현 단계의 세부 계약은 에이전트 개발 SDD에 기록됐으며, 문서 정리는 구현 승인이나 실제 모델 실행 승인으로 해석하지 않는다.

## 8. 재개 상태와 검증 경계

- 현재 단계: 이 절은 최초 Intent 분리 당시의 작업 이력을 보존한다. 최신 상태는 SDD-01~35 인터뷰 종료, §24~25 정합성 정리 및 구현 지시서 작성 완료, 실제 구현 전이다.
- 진행 권한: 의도와 사양 인터뷰, 관련 자료의 읽기와 정본 기록. 데이터 생성, 스키마 변경, 구현, 모델 호출과 배포로 확대하지 않는다.
- 문서 분리 전 코드 상태: 2026-11-03 확인 시 `docs/agent1-review-ui-interviews-1-66`, HEAD `f329be0`. 다른 작업의 브랜치 변경과 미커밋 변경을 보존하며 이 작업에서 브랜치를 전환하지 않는다.
- 이번 변경 범위: 이 파일 생성, 기존 리뷰 Intent에서 이번 에이전트 기획 부분 제거, 문서 안내와 결정 인덱스의 연결 변경. 새 발행 버전은 만들지 않는다.
- 문서 검증 결과: 기존 리뷰 Intent의 확정 리뷰 절부터 문서 끝까지 해시가 동일하고, 리뷰 데이터 SDD와 데이터 승인 기록도 해시가 동일함을 확인했다. 이관한 결정과 미결, 로컬 링크와 새 문서 형식 및 안내와 결정 인덱스의 공백 검사를 확인했다.
- 병행 작업: 분리 작업 도중 리뷰 UI/UX SDD의 제목과 상태가 인터뷰 1~66 확정안으로 갱신되며 해시가 변경된 것을 확인했다. 이 문서 분리에서 해당 SDD를 수정하거나 다른 작업의 변경을 되돌리지 않았다.
- 테스트 범위: 동작 변경 없는 문서 분리이므로 TDD 예외를 적용한다. 앱 회귀, 실제 모델과 도구 실행, 답변 품질과 UI/UX 검증은 수행하지 않는다.
- 다음 행동: 확정한 의도를 기준으로 에이전트 개발 SDD의 범위 해석과 도구 계약, 종료 및 실패 처리, 인수 조건과 구현 순서를 인터뷰한다. 이미 확정한 선택은 다시 묻지 않는다.
