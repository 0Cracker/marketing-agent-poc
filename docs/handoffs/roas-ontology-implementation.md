# ROAS 온톨로지 작업 지시서

작성: 2026-11-10. 상태: 설계 인계, 구현 전. 상세 규칙은 [설계 가이드와 적용 계획](../design/roas-ontology-architecture.md) 하나를 정본으로 사용한다.

## 목표

현재 ROAS, 상품, 캠페인, 운영 기록과 리뷰를 관계로 연결한다. 기존 계산과 조회 Tool을 재사용하고 `ontology_related`를 추가해 일반 방식과 근거 탐색/해석을 비교한다. 별도 그래프 DB는 만들지 않는다.

## 시작할 때

1. 작업 디렉터리는 `marketing-agent-poc/` 하나다. `AGENTS.md`, `docs/README.md`, 설계 정본, 최신 `docs/design/agent-development-sdd.md`를 읽고 `sdlc`, 코딩 시 `ponytail`을 적용한다.
2. 실제 Git 상태와 기존 변경을 확인한다. 문서화 기준 HEAD는 `bc28afe`, 당시 여러 미커밋 변경이 있었다. 현재 상태를 다시 확인하며 다른 작업을 되돌리거나 별도 작업본을 만들지 않는다.
3. 설계 정본 §11의 스키마 변경 제안에 실제 개별 승인이 있는지 확인한다. 없다면 원천 매핑 감사와 구체적 변경 명세를 먼저 완성해 제시한다. 방향 선택과 문서 작성 요청을 스키마/데이터 생성 승인으로 간주하지 않는다.

## 작업 순서

1. **기준선:** 현재 소스, 자료 해시와 관련 회귀 결과를 고정하고 명세/원천의 차이를 기록한다.
2. **공통 흐름:** 일반/온톨로지 양쪽에 Deep 후속 조회 최대 1회를 제공한다. 현재 Jev 5회, Tool 20회 상한과 최종 생성 예산을 유지한다.
3. **온톨로지:** 승인된 ROAS 전용 개념, 관계와 제약, 원천 매핑, 실행별 메모리 인덱스를 구현한다. `nodesById`, 양방향 관계와 출처 참조를 사용한다.
4. **Tool 연결:** 기존 Tool 런타임과 Jev 선택에 `ontology_related`를 추가한다. 최종 입력의 관계 의미/한계를 보존하고 중복 원문을 제거한다.
5. **사용 연결:** 승인된 `analysisMode`와 DB 열, 일반/온톨로지 선택, 로그, 저장/복원과 과거 기록 호환을 연결한다.
6. **검증:** 정본 §10의 기능 검사, 브라우저 확인과 동일 조건 비교를 수행한다. 결과와 미실행은 정본에 이어 기록한다.

## 반드시 지킬 경계

- 홍보 상품과 구매 상품, 전체 성과와 상세 분해, 운영 기록과 사건, 리뷰 전체와 경험별 감성을 구분한다.
- 리뷰를 광고 유입 고객이나 개별 주문에 연결하지 않는다. supports/counters나 인과관계를 원천 사실로 만들지 않는다.
- 기존 계산 함수, 인증, 조회 범위, 취소와 공급자 오류 처리를 보존한다. 답변 자동 검증과 보류는 복원하지 않는다.
- baseline에도 같은 원천/의미 설명과 후속 조회를 제공한다. 온톨로지에만 새 사실을 주지 않는다.
- 원천/manifest 변경, 신규 합성 fixture, 스키마 변경, 모델 호출과 Git 발행을 문서화 요청에서 자동 확대하지 않는다. 승인된 권한 범위에서 진행한다.

## 완료 보고

변경 파일과 이유, 실행한 검사와 실제 결과, 구조/매핑의 원천 근거, 비교 결과, 미검증과 남은 승인 사항을 보고한다. 모의 실행과 실모델 품질, 로컬 반영과 원격 배포를 구분한다. 상세 계획서를 중복 생성하지 않는다.
